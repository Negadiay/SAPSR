# Отчёт v2

**Статус:** черновик на согласование. Готовит Бузычков (19.10.2026). Согласуют Халилов и Котко. Халилов согласовал 23.10.2026 (вопрос 2 закрыт); бэкенд хранит отчёт целиком (`submissions.report`) с 23.10.2026 — ждёт Котко.

Отчёт о проверке пояснительной записки: замечания с местами в документе, происхождение и уверенность каждого замечания, карта требований семестра и сведения о том, как шла проверка. Отчёт приходит в поле `report` сообщений фаз `format` и `content` из протокола очередей (`queue-v2.md`, раздел 5).

| Файл | Что в нём |
|---|---|
| `report-v2.schema.json` | JSON-схема (draft 2020-12). Генерируется из классов `worker-python/sapsr/report/model.py` командой `python tools/export_contract.py`; тест не даёт ей отстать от кода |
| `examples/report-v2/format.json` | фаза `format`: замечание оформления на нескольких страницах |
| `examples/report-v2/contradiction.json` | фаза `content`: противоречие с двумя фрагментами |
| `examples/report-v2/requirements.json` | фаза `content`, 7-й семестр: карта требований, требование «не удалось установить» |

Примеры собраны настоящей цепочкой проверки на документах `test-fixtures/hybrid`. Ответы модели в них — сценарная заглушка из тестов, поэтому в `pipeline.models` подставлены модель и квантование из решения 1, а время этапов убрано.

## 1. Общие правила

- JSON в UTF-8, имена полей — `snake_case`, в корне `schema: 2`.
- Поля со значением `null` в отчёт не пишутся: отсутствующее поле читается как `null`. Получатель пропускает незнакомые поля — так поля можно добавлять, не ломая другую сторону.
- Отчёт фазы `format` содержит только замечания оформления и структуры. Отчёт фазы `content` — **полный**: в нём те же замечания оформления плюс содержательные, и он заменяет отчёт фазы `format`.
- Номера страниц — с 1, по PDF-версии работы (решение 3: работа из DOCX проверяется в PDF-версии).
- Координаты (`bbox`) — в пунктах PDF, начало в левом верхнем углу страницы: `[x0, top, x1, bottom]`.
- Повторная проверка того же файла с той же версией базы знаний и модели даёт тот же отчёт: те же замечания под теми же номерами. Отличаются только времена этапов.

## 2. Верхний уровень

```json
{
  "schema": 2,
  "phase": "content",
  "profile": { "id": "sem7", "title": "…", "work_type": "course_project", "semester": 7, "stage": 2, "is_default": false },
  "summary": { "passed": true, "blocking": 0, "findings": 5, "by_category": { … }, "by_severity": { … }, "needs_teacher_review": 4, "content_checked": true },
  "findings": [ … ],
  "requirements": [ … ],
  "document": { "pages": 8, "source_format": "pdf", "main_font": "…", "main_size": 14.0, "title_page": { … } },
  "pipeline": { "mode": "hybrid", "worker_version": "2.0.0", "kb_version": "2026.10.18+a5116066", … }
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `schema` | число | всегда `2` |
| `phase` | строка | `format` или `content` — какой фазой отправлен отчёт |
| `profile` | объект | по каким требованиям проверено (раздел 6) |
| `summary` | объект | счётчики для списка работ и уведомлений (раздел 7) |
| `findings` | массив | замечания (раздел 3); упорядочены: сначала блокирующие, затем по категориям и серьёзности |
| `requirements` | массив | карта требований семестра (раздел 4); пустой, если профиль их не проверяет или это фаза `format` |
| `document` | объект | сведения о проверенном файле (раздел 5) |
| `pipeline` | объект | как шла проверка: версии, этапы, что пропущено и почему (раздел 8) |

## 3. Замечание — `findings[]`

```json
{
  "id": "f-001",
  "requirement_id": "CNT-CONSIST-002",
  "category": "content",
  "status": "violated",
  "severity": "major",
  "origin": "hybrid",
  "confidence": 1.0,
  "needs_teacher_review": false,
  "blocking": false,
  "title": "Согласованность перечней",
  "message": "«Форматы входных файлов»: перечни в разных частях записки не совпадают.",
  "expected": "Одинаковый перечень во всех разделах.",
  "found": "Введение: DOCX, PDF; подраздел 1.2: PDF.",
  "evidence": [
    { "page": 3, "quote": "Система принимает файлы в форматах DOCX и PDF", "block_id": "b-0028", "section": "Введение" },
    { "page": 4, "quote": "Входные данные системы — только файл пояснительной записки в формате PDF", "block_id": "b-0038", "section": "1.2" }
  ],
  "source": { "doc": "Требования к системе, 7 семестр" },
  "fix": "Приведите описание к одному варианту.",
  "page": "3–4",
  "location": "Страницы: 3–4",
  "rule": "Одинаковый перечень во всех разделах.",
  "context": "Система принимает файлы в форматах DOCX и PDF | …"
}
```

| Поле | Тип | Обязательно | Что значит |
|---|---|---|---|
| `id` | строка | да | номер замечания в отчёте: `f-001`, `f-002`… Стабилен при повторной проверке того же файла |
| `requirement_id` | строка | да | идентификатор правила из базы знаний (`FMT-MARGIN-LEFT`, `CNT-CONSIST-001`) или требования семестра (`REQ7-INTEGRATION`). Каталог — `worker-python/kb/rules/*.yaml` |
| `category` | строка | да | `structure`, `format`, `integrity`, `content`, `requirements` — таблица ниже |
| `status` | строка | нет, по умолчанию `violated` | `violated` — нарушение установлено; `not_established` — не удалось установить; `disputed` — свидетельства противоречат друг другу |
| `severity` | строка | да | `critical`, `major`, `minor`, `info` |
| `origin` | строка | да | кто вынес решение — таблица ниже |
| `confidence` | число 0–1 | нет | только у `neural` и `hybrid`: наименьшая уверенность в фактах, на которых стоит замечание |
| `needs_teacher_review` | логическое | нет, по умолчанию `false` | замечание требует проверки преподавателем: уверенность ниже порога профиля или правило так помечено (скрытый текст, ФИО на титуле) |
| `blocking` | логическое | да | блокирует сдачу. **Бывает `true` только у `origin: symbolic`** (решение 5) |
| `title` | строка | нет | краткое название правила — для группировки |
| `message` | строка | да | замечание одной фразой |
| `expected` | строка | нет | что требуется |
| `found` | строка | нет | что найдено |
| `evidence` | массив | нет | места в документе (ниже). У противоречия — **два** места, у замечания по нескольким страницам — по месту на страницу. Пустой — замечание ко всему документу |
| `source` | объект | нет | норматив: `doc` и `clause` (пункт). `clause` отсутствует — пункт ещё не сверен с текстом документа |
| `fix` | строка | нет | как исправить |
| `page`, `location`, `rule`, `context` | | нет | поля отчёта v1 на переходный период (раздел 10) |

**Место в документе — `evidence[]`:**

| Поле | Что значит |
|---|---|
| `page` | страница |
| `quote` | дословный фрагмент документа. У содержательных замечаний цитата проверена: она есть в тексте |
| `block_id` | блок модели документа (`b-0028`) — для отладки и будущей подсветки |
| `section` | раздел: номер (`1.2`) или заголовок (`Введение`) |
| `bbox` | прямоугольник на странице (пока заполняется у скрытого текста) |

**Категории:**

| `category` | Подпись в интерфейсе | Примеры правил |
|---|---|---|
| `structure` | Структура | обязательные разделы, нумерация разделов, титульный лист, число источников |
| `format` | Оформление | поля, шрифт, интервал, отступ, списки, ссылки на рисунки, библиография |
| `integrity` | Целостность | скрытый текст, ФИО на титуле не совпадает с зарегистрированным |
| `content` | Содержание | противоречия в описании системы, заявленное, но не описанное |
| `requirements` | Требования семестра | требование нарушено, не установлено или спорно |

**Происхождение:**

| `origin` | Что значит | Подпись в интерфейсе | Может блокировать |
|---|---|---|---|
| `symbolic` | правило над данными извлечения и разметки документа | «правило» | да |
| `hybrid` | факты извлекла языковая модель, решение вынесло правило; цитаты проверены символьно | «правило + модель» | нет |
| `neural` | замечание сформулировала модель (только режим сравнения `neural`) | «модель» | нет |

**Уверенность.** В интерфейсе (И4) — не процент, а три уровня: «высокая» при `confidence` ≥ 0,85, «средняя» от 0,6 до 0,85, «низкая» ниже 0,6 (подтвердил Халилов 23.10.2026). Порог «требует проверки преподавателем» — в профиле (`review_threshold`, сейчас 0,75), его отражает `needs_teacher_review`.

## 4. Требования семестра — `requirements[]`

```json
{ "id": "REQ7-NEURAL-ROLE", "title": "Нейросетевой компонент участвует в решении", "status": "satisfied",
  "confidence": 0.9, "needs_teacher_review": false,
  "evidence": [ { "page": 5, "quote": "Нейросетевая модель разметки получает строки документа с координатами…",
                  "block_id": "b-0044", "section": "2.1" } ],
  "source": { "doc": "Требования к системе, 7 семестр" } }
{ "id": "REQ7-INTEGRATION", "title": "Точки интеграции описаны явно", "status": "not_established",
  "needs_teacher_review": true, "evidence": [], "note": "Подходящих фрагментов не найдено.",
  "source": { "doc": "Требования к системе, 7 семестр" } }
```

| `status` | Подпись | Когда |
|---|---|---|
| `satisfied` | выполнено | есть проверенное подтверждение с уверенностью не ниже порога и нет противоречащих |
| `violated` | нарушено | есть проверенное противоречие и нет подтверждений |
| `disputed` | спорно | есть и подтверждения, и противоречия; или раздела, где ждём свидетельство, нет, а подтверждение нашлось в другом месте — правило и модель расходятся, показываются оба результата |
| `not_established` | не удалось установить | свидетельств нет или модель неуверенна; `note` поясняет |
| `not_applicable` | не применимо на этом этапе | требование проверяется на других опроцентовках |

По требованиям со статусами `violated`, `disputed`, `not_established` в `findings` есть и замечание: `category: requirements`, `requirement_id` — идентификатор требования. Если модель не отвечала, требование получает `not_established` с `note` «Не оценивалось…» без замечания, а причина — в `pipeline.skipped`.

Набор требований 7-го семестра — `worker-python/kb/requirements/sem7.yaml`: девять требований, сверены 23.10.2026 с разделом 16 методички (с. 57–63). Пунктов с номерами там нет — в `source.clause` подраздел и страница. Этапы — по требованиям к опроцентовкам (раздел 12, с. 32–35): требования к архитектуре проверяются на 2-й и 3-й, к тестированию и эффективности — на 3-й. Семестр и этап сервер берёт по группе студента и учебному календарю (решение 11).

## 5. Документ — `document`

| Поле | Что значит |
|---|---|
| `pages` | число страниц |
| `sha256` | хэш файла |
| `source_format` | `pdf` или `docx` — из задания |
| `main_font`, `main_size` | основной шрифт и размер, как их увидел разметчик |
| `title_page.student_name` | ФИО студента с титульного листа, как написано («И.И. Иванов») |
| `title_page.matches_registration` | совпадает ли фамилия с зарегистрированной (`student.last_name` задания); отсутствует — сравнить не с чем |
| `title_page.work_type` | **26.10.2026**: вид работы по титульному листу — `course_work`, `course_project`, `diploma` — по словам «к курсовому проекту», «курсовая работа», «дипломный проект» или обозначению «БГУИР КП7 …»; отсутствует — не распознан. Студент вид работы не выбирает: бэкенд записывает его в работу, дипломную — только в 8 семестре (решение 11) |

Ответ на вопрос Котко (К2) — в каком поле ФИО с титульного листа: `document.title_page`. Несовпадение даёт ещё и замечание `TTL-STUDENT-MATCH` (`needs_teacher_review: true`, сдачу не блокирует).

## 6. Профиль — `profile`

| Поле | Что значит |
|---|---|
| `id`, `title` | профиль из `worker-python/kb/profiles` |
| `work_type`, `semester`, `stage` | поля профиля из задания |
| `is_default` | `true` — в задании профиль не указан или для него нет профиля в базе знаний: применены базовые требования (в `pipeline.warnings` — `DEFAULT_PROFILE` или `PROFILE_NOT_FOUND`) |

Значения `work_type` (вопрос 2 протокола очередей): `course_work`, `course_project`, `diploma`.

## 7. Сводка — `summary`

| Поле | Что значит |
|---|---|
| `passed` | блокирующих замечаний нет; то же, что `passed` в сообщении фазы |
| `blocking` | число блокирующих замечаний |
| `findings` | всего замечаний |
| `by_category`, `by_severity` | счётчики для уведомлений: отдельно оформление и содержание (К6) |
| `needs_teacher_review` | сколько замечаний требуют проверки преподавателем |
| `content_checked` | содержательная проверка выполнялась (в отчёте фазы `format` — всегда `false`) |

## 8. Сведения о проверке — `pipeline`

| Поле | Что значит |
|---|---|
| `mode` | `hybrid` — целевая цепочка; `symbolic` — только правила; `neural` — модель сама пишет замечания (режимы сравнения, З10) |
| `worker_version` | версия обработчика |
| `kb_version` | версия базы знаний: версия каталога + хэш содержимого `kb/` — меняется при любой правке правил |
| `models[]` | `role` (`layout` — разметка блоков, `llm` — языковая модель), `name`, `version`, `quantization`, `provider`, `cloud` |
| `prompts[]` | версии подсказок модели (`claims` v1…) |
| `stages[]` | этапы цепочки с `status` (`done`, `skipped`, `failed`) и временем `ms` |
| `skipped[]` | что не проверялось и почему: `id` (правило, требование, `*` — весь этап), `stage`, `reason`, `message` |
| `warnings[]` | предупреждения: `code`, `message` |
| `metrics` | числа для замеров (З10, Ж8) |

**Причины пропуска (`skipped[].reason`):**

| Код | Что значит |
|---|---|
| `IIS_UNAVAILABLE` | справочник ИИС недоступен — сверка с ним не выполнялась |
| `LLM_UNAVAILABLE` | языковая модель выключена или не отвечает — содержательная проверка не выполнялась |
| `LLM_SCHEMA` | ответ модели дважды не прошёл JSON-схему — раздел пропущен |
| `TIMEOUT` | истекло время проверки — оставшиеся разделы или требования пропущены |
| `BUDGET` | текст не поместился в бюджет модели — проверены разделы с наибольшим приоритетом |
| `NO_SECTIONS` | в записке не нашлось разделов для содержательной проверки |
| `NO_TEXT_LAYER` | в документе нет текста — остальные правила не выполнялись |
| `CHECK_ERROR` | проверка завершилась ошибкой и пропущена (остальные выполнены) |
| `MODE_SYMBOLIC`, `MODE_NEURAL`, `DISABLED` | этап выключен режимом или профилем |

**Предупреждения (`warnings[].code`):** `DEFAULT_PROFILE`, `PROFILE_NOT_FOUND`, `CONVERTED_FROM_DOCX` (проверена PDF-версия работы из DOCX), `CLOUD_LLM` (текст обрабатывала облачная модель, включённая настройкой — решение 2).

**Метрики:** `pages`, `blocks`, `sections`; `content_fragments`, `content_chars_dropped`; `claims_extracted`, `claims_accepted`, `claims_rejected_quote`, `claims_rejected_value`, `claims_hallucinated_quote_share` — доля выдуманных цитат; `reasoning_firings`; `requirements_checked`, `requirements_quotes_rejected`; `llm_calls`, `llm_cache_hits`, `llm_schema_retries`, `llm_schema_failures`, `llm_errors`, `llm_ms`. В режиме `neural` — `neural_findings`, `neural_quotes`, `neural_quotes_unverified`.

## 9. Что нужно экрану отчёта (план Халилова, И4)

| На экране | Откуда |
|---|---|
| Сводка и счётчики, «требуют проверки преподавателем» | `summary` |
| Группировка и фильтры по категории, серьёзности, странице | `category`, `severity`, `evidence[].page` |
| Карточка: сообщение, ожидалось / найдено, рекомендация | `message`, `expected`, `found`, `fix` |
| Цитаты со страницей и разделом; противоречие — два фрагмента рядом | `evidence[]` |
| Источник требования «СТП 01-2024, п. …» | `source.doc`, `source.clause` |
| Метка «правило», «модель», «правило + модель» | `origin` |
| Уверенность словами, пометка «требует проверки» | `confidence`, `needs_teacher_review` |
| Блок «Не проверено» с причинами | `pipeline.skipped` |
| Карта покрытия требований | `requirements` |
| Сведения о проверке: версии моделей и базы правил, время этапов | `pipeline.models`, `pipeline.kb_version`, `pipeline.stages` |
| «Объяснить» | пока нет — см. открытые вопросы |

## 10. Переход с v1

- В каждом замечании оставлены поля отчёта v1: `severity`, `page` (число или диапазон «3–5, 9»), `location`, `message`, `rule`, `found`, `fix`, `context` — генерация PDF-отчёта и экран «Мои работы» продолжают работать.
- Результат v1 — `{task_id, status, errors}` (`SAPSR_QUEUE_PROTOCOL=1`) бэкенд по-прежнему принимает. В нём `errors` — те же замечания, но `severity` отражает блокировку: неблокирующее замечание уровня `major` (например, содержательное) приходит как `warning`, чтобы счётчики «ошибок» в уведомлении совпадали со статусом. В `errors` есть и поля v2: `requirement_id`, `origin`, `blocking`, `needs_teacher_review`, `confidence`.
- С 23.10.2026 (задача 5.2) в `docker-compose.yml` по умолчанию `SAPSR_QUEUE_PROTOCOL=2` — прогресс, две фазы и `failed`. Бэкенд хранит отчёт v2 целиком (`submissions.report`), а в `format_errors` кладёт его замечания в форме v1 с той же `severity`, что и обработчик в v1.
