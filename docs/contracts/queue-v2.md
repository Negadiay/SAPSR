# Протокол очередей v2

**Статус:** черновик на согласование. Готовит Котко (черновик от 18.10.2026 подготовил Халилов). Согласуют Бузычков и Жерко.

Описывает обмен бэкенда и обработчика через RabbitMQ: задание на проверку, сообщения о ходе проверки и результат в две фазы. Формат самого отчёта задаёт контракт «Отчёт v2» — `report-v2.md`, схема `report-v2.schema.json`; здесь отчёт показан сокращённо.

Те же примеры лежат файлами в `examples/queue-v2/`. По `task.json` тест бэкенда проверяет, что задание собирается ровно с этими полями, поэтому при изменении формата правьте и этот документ, и файлы.

## 1. Очереди

| Очередь | Кто пишет → кто читает | Что передаётся | Есть сейчас |
|---|---|---|---|
| `pdf_tasks_queue` | бэкенд → обработчик | задание на проверку | да |
| `pdf_progress_queue` | обработчик → бэкенд | текущий этап проверки | нет, новая |
| `pdf_results_queue` | обработчик → бэкенд | результат фазы или сбой | да |
| `pdf_dead_letter_queue` | RabbitMQ | сообщения, которые не удалось обработать | нет, предложение (раздел 7) |

Все очереди долговечные (`durable`), сообщения — с сохранением на диск (`delivery_mode = 2`).

## 2. Общие правила

- Тело — JSON в UTF-8, свойство сообщения `content_type = application/json`. Имена полей — `snake_case`.
- Строки руками не склеиваются: бэкенд собирает сообщения из классов-записей Java и сериализует их через Jackson, обработчик — через `json.dumps` или pydantic. Кавычка в имени файла или в ФИО больше ничего не ломает.
- В каждом сообщении есть `schema: 2`. Сообщение без поля `schema` считается сообщением прежнего формата (v1, раздел 8).
- Получатель игнорирует незнакомые поля: так новые поля можно добавлять, не ломая другую сторону. Необязательное поле может прийти со значением `null`.
- `task_id` — номер работы в базе (`submissions.id`).
- `trace_id` — идентификатор UUID, создаётся бэкендом при загрузке. Обработчик возвращает его в каждом сообщении о прогрессе и результате и пишет в каждую строку своего лога. По нему Жерко связывает логи двух сервисов.
- Spring добавляет к сообщению заголовок `__TypeId__` с именем класса — обработчику он не нужен, его можно не читать.

## 3. Задание — `pdf_tasks_queue`

```json
{
  "schema": 2,
  "task_id": 153,
  "type": "CHECK",
  "file": {
    "storage_key": "2026/10/8f3a2c1e-5b7d-4e2a-9c4f-1a2b3c4d5e6f.pdf",
    "sha256": "9f2c4e8a1b3d5f7092a4c6e8b0d2f4a6c8e0b2d4f6a8c0e2b4d6f8a0c2e4b6d8",
    "source_format": "pdf"
  },
  "profile": { "work_type": "course_work", "semester": 7, "stage": 2 },
  "student": { "last_name": "Иванов", "first_name": "Иван", "group": "321702" },
  "previous": null,
  "trace_id": "4b1e0c7a-2f3d-4a5b-8c6d-7e8f9a0b1c2d",
  "file_path": "/app/storage/2026/10/8f3a2c1e-5b7d-4e2a-9c4f-1a2b3c4d5e6f.pdf"
}
```

| Поле | Тип | Обязательно | Что значит |
|---|---|---|---|
| `schema` | число | да | всегда `2` |
| `task_id` | число | да | номер работы |
| `type` | строка | да | вид задания; пока только `CHECK` — проверить работу |
| `file.storage_key` | строка | да | путь к файлу относительно корня хранилища, см. ниже |
| `file.sha256` | строка | да | хэш SHA-256 файла, 64 шестнадцатеричных символа. Можно сверить с файлом и использовать как ключ кэша |
| `file.source_format` | строка | да | исходный формат: `pdf` или `docx`. Файл по ключу **всегда PDF**: DOCX конвертируется при загрузке (решение 3). Пока конвертация не сделана, всегда `pdf` |
| `profile.work_type` | строка | нет | вид работы: `course_work` (курсовая работа), `course_project` (курсовой проект), `diploma` (дипломный проект). Значения согласовать с каталогом профилей `kb/profiles` |
| `profile.semester` | число | нет | семестр, 1–12 |
| `profile.stage` | число | нет | номер опроцентовки, 1–3 |
| `student.last_name` | строка | нет | фамилия — для сверки с титульным листом |
| `student.first_name` | строка | нет | имя; у пользователей, зарегистрированных по старой форме, — `null` (известны только инициалы) |
| `student.group` | строка | нет | номер группы, 6 цифр |
| `previous` | объект | нет | предыдущая версия той же работы. Пока всегда `null`; появится вместе со связью версий: `{ "task_id": 140, "annotations": [ … ] }` |
| `trace_id` | строка | да | сквозной идентификатор |
| `file_path` | строка | да, временно | абсолютный путь к тому же файлу. Оставлен только на переходный период, чтобы нынешний `main.py` работал без правок. Обработчику переходить на `storage_key`; после перехода поле удаляется |

Если весь `profile` пустой (интерфейс пока не спрашивает вид работы, семестр и этап), обработчик применяет базовый профиль и пишет об этом предупреждение в отчёт. ФИО студента — персональные данные: в логи их не писать.

**Хранилище файлов.** Оба сервиса знают корень хранилища из настроек: бэкенд — `sapsr.storage.root` (по умолчанию `../storage`, в Docker это `/app/storage`), обработчик — предлагается переменная окружения `SAPSR_STORAGE_ROOT` (в Docker `/app/storage`). В Docker Compose корень у обоих — общий том `storage`.

- Файл хранится под сгенерированным именем: `<год>/<месяц>/<UUID>.pdf`. Исходное имя файла в задание не попадает — оно есть только в базе (`submissions.original_file_name`).
- Путь к файлу = корень + `storage_key`. Обработчик проверяет, что получившийся путь не выходит за корень: ключ из очереди — тоже входные данные.
- Работы, загруженные до перехода на ключи, лежат в корне хранилища под старыми именами; их ключ — просто имя файла.

## 4. Прогресс — `pdf_progress_queue`

```json
{ "schema": 2, "task_id": 153, "stage": "structure", "index": 2, "total": 6, "trace_id": "4b1e0c7a-2f3d-4a5b-8c6d-7e8f9a0b1c2d" }
```

Обработчик отправляет сообщение в начале каждого этапа. Этапы — по целевой цепочке обработки:

| `index` | `stage` | Что происходит | Подпись в интерфейсе |
|---|---|---|---|
| 1 | `extract` | извлечение символов, строк и координат | Извлечение текста |
| 2 | `structure` | разметка логических блоков нейросетью | Структура |
| 3 | `format` | правила оформления и структуры | Оформление |
| 4 | `claims` | языковая модель: утверждения и свидетельства | Содержание |
| 5 | `reasoning` | правила: конфликты утверждений, требования семестра | Содержание |
| 6 | `report` | сборка итогового отчёта | Отчёт |

- Список этапов подтверждён Бузычковым 19.10.2026 — так их и отправляет обработчик (`worker-python/sapsr/pipeline.py`).
- `total` всегда 6. Пропущенный этап (например, модель выключена) просто не присылается. Если работа отклонена по оформлению или содержательная проверка не выполняется, после `format` сразу приходит результат фазы `format` с `final: true` — этапов 4–6 не будет.
- Прогресс — вспомогательный: потерянное сообщение ничего не ломает. Бэкенд хранит последний этап в `pipeline_stage`, сообщение с меньшим `index`, чем уже записанный, игнорирует. Интерфейс получает этап обычным опросом списка работ раз в 2–3 секунды.

## 5. Результат — `pdf_results_queue`

Результат приходит **в две фазы** (решение 5): сначала оформление, потом содержание. Плюс отдельная фаза для сбоя.

**Фаза `format`** — после этапов 1–3, быстро:

```json
{
  "schema": 2,
  "task_id": 153,
  "phase": "format",
  "passed": true,
  "final": false,
  "report": {
    "schema": 2,
    "findings": [
      {
        "id": "f-003",
        "requirement_id": "FMT-MARGIN-LEFT",
        "category": "format",
        "severity": "major",
        "origin": "symbolic",
        "blocking": false,
        "message": "Левое поле меньше допустимого.",
        "evidence": [ { "page": 4 } ],
        "fix": "Установите левое поле 30 мм."
      }
    ],
    "pipeline": { "skipped": [] }
  },
  "trace_id": "4b1e0c7a-2f3d-4a5b-8c6d-7e8f9a0b1c2d"
}
```

**Фаза `content`** — после этапов 4–6, позже:

```json
{
  "schema": 2,
  "task_id": 153,
  "phase": "content",
  "passed": true,
  "final": true,
  "report": { "schema": 2, "findings": [ "… замечания оформления и содержания …" ], "pipeline": { "skipped": [] } },
  "trace_id": "4b1e0c7a-2f3d-4a5b-8c6d-7e8f9a0b1c2d"
}
```

**Фаза `failed`** — проверка не удалась:

```json
{
  "schema": 2,
  "task_id": 153,
  "phase": "failed",
  "final": true,
  "error": { "code": "PDF_ENCRYPTED", "message": "Файл защищён паролем. Сохраните его без пароля и загрузите снова." },
  "trace_id": "4b1e0c7a-2f3d-4a5b-8c6d-7e8f9a0b1c2d"
}
```

| Поле | Тип | В каких фазах | Что значит |
|---|---|---|---|
| `schema` | число | все | всегда `2` |
| `task_id` | число | все | номер работы из задания |
| `phase` | строка | все | `format`, `content` или `failed` |
| `passed` | логическое | `format`, `content` | `true` — блокирующих замечаний нет, работа принимается. Блокировать может только замечание символьного происхождения (решение 5); фаза `content` это решение не меняет и повторяет его, чтобы бэкенд справился, даже если `format` потерялся |
| `final` | логическое | все | `true` — по этому заданию больше ничего не придёт. У `format` бывает `true`, если работа отклонена по оформлению или содержательная проверка выключена |
| `report` | объект | `format`, `content` | отчёт v2. В `format` — замечания оформления и структуры; в `content` — **полный** отчёт, который заменяет присланный в `format` |
| `error.code` | строка | `failed` | код сбоя: `FILE_NOT_FOUND`, `PDF_UNREADABLE`, `PDF_ENCRYPTED`, `TOO_LARGE`, `TIMEOUT`, `INTERNAL` |
| `error.message` | строка | `failed` | понятный студенту текст на русском, без трассировок и путей на диске |
| `trace_id` | строка | все | из задания |

## 6. Что делает бэкенд

**Порядок событий:**

| Событие | Состояние работы | Уведомления |
|---|---|---|
| загрузка | `QUEUED`, файл сохранён, задание отправлено | — |
| первое сообщение о прогрессе | `PROCESSING`, `pipeline_stage` обновляется | — |
| `format`, `passed: false` | `REJECTED`, отчёт сохранён | студенту — замечания оформления |
| `format`, `passed: true`, `final: false` | остаётся `PROCESSING`, отчёт сохранён, запускается отсчёт тайм-аута содержательной проверки | студенту — «оформление в порядке, содержание ещё проверяется» |
| `format`, `passed: true`, `final: true` | `SUCCESS` | студенту; преподавателю — работа на проверку |
| `content` до тайм-аута | `SUCCESS`, отчёт заменён полным | студенту — итог; преподавателю — работа на проверку со счётчиками по оформлению и содержанию |
| тайм-аут содержательной проверки | `SUCCESS`, в отчёт добавлена пометка «содержательная проверка не завершилась за N минут» | преподавателю — работа на проверку |
| `content` после тайм-аута | статус не меняется, отчёт заменяется полным | повторно не шлются |
| `failed` до `format` | `FAILED` | студенту — `error.message` и предложение загрузить снова |
| `failed` после `format` с `passed: true` | как при тайм-ауте: `SUCCESS` с отчётом оформления, пометка «содержательная проверка не удалась» | преподавателю — работа на проверку |
| сторож: нет `format` дольше `stuck-timeout` с начала обработки | `FAILED` | студенту — «проверка не завершилась, загрузите снова» |

«Работа уходит преподавателю» — это переход в `SUCCESS`: только такие работы попадают в его очередь. Так сбой или медленная модель не задерживают сдачу (решение 5).

Сейчас интерфейс знает статусы `PROCESSING`, `SUCCESS`, `REJECTED`. `QUEUED` и `FAILED` появятся вместе с приёмом фаз, и интерфейс нужно научить им заранее.

**Тайм-аут содержательной проверки** отсчитывается от получения фазы `format`. Величина в решении 5 ещё не утверждена, поэтому это настройка со значением 5 минут.

**Повторы.** RabbitMQ может доставить сообщение дважды. Ключ — пара (`task_id`, `phase`): повторное сообщение той же фазы может перезаписать отчёт, но второе уведомление не отправляется. Результат по работе, которой уже нет (студент отозвал), или по работе в `FAILED` записывается в лог и пропускается.

**Настройки бэкенда:**

| Настройка | Значение по умолчанию | Зачем | Есть в коде |
|---|---|---|---|
| `sapsr.pipeline.content-timeout` | `5m` | тайм-аут содержательной проверки, решение 5 | в настройках есть; читать её будет приём двух фаз |
| `sapsr.pipeline.stuck-timeout` | `15m` (предложение) | сторож для зависших работ | нет |
| `sapsr.storage.root` | `../storage` | корень хранилища файлов | да |
| `sapsr.rabbitmq.tasks-queue` | `pdf_tasks_queue` | очередь заданий | да |
| `sapsr.rabbitmq.results-queue` | `pdf_results_queue` | очередь результатов | да |
| `sapsr.rabbitmq.progress-queue` | `pdf_progress_queue` | очередь прогресса | нет |

## 7. Ошибки и недоставленные сообщения

- Обработчик ловит любую ошибку при проверке, отправляет фазу `failed` и подтверждает задание. Задание не должно возвращаться в очередь и снова ронять обработчик.
- Сообщение, которое нельзя разобрать (не JSON, нет `task_id`, незнакомое значение `schema`), получатель отклоняет без возврата в очередь (`basic_reject` с `requeue = false`). RabbitMQ перекладывает его в очередь недоставленных — оно не теряется и не крутится по кругу.
- **Предложение для Жерко:** очередь недоставленных подключать политикой RabbitMQ, а не аргументами очереди. Аргументы уже объявленной очереди менять нельзя: оба сервиса объявляют очереди при старте, и объявление с другими аргументами падает с ошибкой `PRECONDITION_FAILED`. Политика применяется к уже существующим очередям:

  ```
  rabbitmqctl set_policy sapsr-dlx "^pdf_(tasks|progress|results)_queue$" '{"dead-letter-exchange":"sapsr.dlx"}' --apply-to queues
  ```

  Плюс обменник `sapsr.dlx` типа `fanout` и привязанная к нему очередь `pdf_dead_letter_queue`. Всё это можно описать в файле определений RabbitMQ и загружать при старте контейнера.

## 8. Переход с v1

Сейчас (v1) задание — `{ "task_id", "file_path", "status" }`, а результат — `{ "task_id", "status": "SUCCESS" | "FAIL", "errors": [ … ] }`, одной фазой.

| Шаг | Кто | Состояние |
|---|---|---|
| 1. Бэкенд отправляет задание v2, сохраняя `file_path` | Котко | **сделано 18.10.2026** |
| 2. Бэкенд принимает результаты и v1, и v2; слушает очередь прогресса | Котко | следующий шаг |
| 3. Обработчик читает `storage_key`, отправляет прогресс и результат v2 | Бузычков | **готово 19.10.2026**: `storage_key` читается всегда (с проверкой выхода за корень, `file_path` — запасной путь); прогресс и фазы включаются переменной `SAPSR_QUEUE_PROTOCOL=2` после шага 2, до этого результат v1 |
| 4. Убрать из задания `file_path`, а из бэкенда — приём v1 | Котко | после шага 3 |

До шага 2 обработчик продолжает присылать результат в формате v1.
