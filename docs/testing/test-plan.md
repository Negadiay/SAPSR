# План тестирования SAPSR

Что и как проверяется к 3-й опроцентовке (26.11.2026). Результаты запусков — в соседних файлах: `e2e-results.md` (сквозные сценарии), `quality.md` (качество и сравнение режимов), `performance.md` (эффективность), `unit-summary.md` (модульные тесты).

## 1. Процедура

| Что | Как |
|---|---|
| Среда | ноутбук ThinkPad P16v (RTX A500 4 ГБ, 32 ГБ ОЗУ), Windows 11, Docker Desktop; Python 3.12, Java 21, Node 20 |
| Языковая модель | `qwen3.5:4b` в Ollama, температура 0, seed 42, окно 8192 токена. Для повторяемости тесты идут на записанных ответах этой модели (режим `replay`, `test-fixtures/llm-replay`) или на сценарной заглушке (`stub`); живая модель — в оценке эффективности |
| База знаний | `worker-python/kb`, версия печатается в каждом отчёте (`pipeline.kb_version`) и в шапке каждого файла результатов |
| Порядок | 1) модульные тесты трёх частей; 2) оценка качества на корпусе в трёх режимах; 3) сквозные сценарии в изолированном составе; 4) замеры эффективности |
| Команды | обработчик — `python -m pytest -q`; бэкенд — `mvnw test "-Dtest=!BackendApplicationTests"`; интерфейс — `npm test`; качество — `python tools/evaluate.py --out ../docs/testing/quality`; сквозные — `pwsh -File scripts\e2e.ps1`; эффективность — `python tools/measure.py` |
| Фиксация результатов | таблицы Markdown и CSV в `docs/testing/`; у каждого файла — шапка «Среда» (дата, машина, модель, версия базы знаний, команда) |
| Изоляция | сквозные сценарии идут в отдельном проекте Docker Compose с фальшивым токеном бота: рабочая база и пользователи не затрагиваются, сообщения в Telegram не уходят. Тест `BackendApplicationTests` не запускается никогда — он поднимает бота с настоящим токеном |
| Тестовые данные | корпус `test-fixtures/hybrid` — 20 вымышленных записок с разметкой в `expected.json` (генератор `generate.py`); образец DOCX — `test-fixtures/docx`; файл с пометками преподавателя — `test-fixtures/review`. Работы настоящих студентов не используются |

**Группы тестов:** типичные — основные сценарии использования; граничные — редкие и предельные сочетания условий; отрицательные — некорректные входные данные и отказы компонентов.

## 2. Критерии приемлемости

Из требований раздела 1 записки:

| № | Критерий | Где проверяется |
|---|---|---|
| К1 | все типичные сквозные сценарии проходят | `e2e-results.md` |
| К2 | на граничных и отрицательных тестах нет аварийных отказов: работа получает итог или понятный отказ, обработчик не перезапускается | `e2e-results.md` (E2E-13), модульные тесты |
| К3 | проверка оформления документа до 100 страниц — не дольше 60 с | `performance.md` |
| К4 | полный отчёт по документу до 60 страниц — не дольше 5 мин | `performance.md` |
| К5 | ложных блокирующих замечаний на корректных документах — 0 | `quality.md` |
| К6 | блокирующих замечаний от языковой модели — 0 (блокирует только правило над данными документа) | `quality.md` |
| К7 | при одинаковых входах и модели отчёт повторяется | `quality.md` (воспроизводимость) |
