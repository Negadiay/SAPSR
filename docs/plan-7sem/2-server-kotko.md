## 0. Общий контекст (одинаков во всех четырёх документах)

### Что требует 7-й семестр

Методичка («Требования к системе.pdf») требует **гибридную** систему: символьная часть (база знаний, правила, вывод) и статистическая/нейросетевая часть должны вместе решать одну задачу. Из неё напрямую следует:

- нейросетевой компонент реально участвует в цепочке решения, а не «упомянут»; имитация гибридности прямо названа недопустимой;
- символьный компонент обеспечивает проверяемость и объяснимость итогового решения;
- точки интеграции описаны явно: что, в каком формате и на каком шаге передаётся между компонентами;
- предусмотрена обработка рассогласований: неуверенный ответ модели, отсутствие знаний в базе, противоречие между правилом и моделью;
- компоненты заменяются независимо друг от друга;
- есть методика тестирования: компонентные, интеграционные и сквозные тесты в трёх группах (типичные, граничные, отрицательные), результаты в таблицах;
- есть оценка эффективности (время отклика, нагрузка модели) и, желательно, сравнение гибридного варианта с чисто символьным и чисто нейросетевым.

Во введении и аналитическом разделе записки мы уже пообещали конкретное: распознавание структуры документа нейросетью, извлечение утверждений о системе языковой моделью, поиск противоречий правилами, проверку требований семестра, объяснения с опорой на нормативы.

Mini App (React) ──REST──► Backend (Spring Boot) ──► PostgreSQL

## 2. Что сейчас в коде и почему это мешает

**Данные.**

- ФИО и группа студента лежат одной строкой `full_name` вида «Иванов И.И. (гр. 321702)»; группа достаётся обратно регулярным выражением (`TeacherController.extractGroupNumber`). Отсюда и проблема одинаковых имён: два Иванова И.И. из одной группы для преподавателя неразличимы.
- Группы преподавателя — JSON-строка в `users.teacher_groups`.
- Схема живёт в `init.sql` с дописанными `ALTER TABLE`; в примере настроек `ddl-auto=validate`, а в рабочих у вас `update` — то есть реальная схема у каждого своя.
- В `init.sql` зашит реальный преподаватель с Telegram ID.
- `GET /teachers` отдаёт студентам Telegram ID преподавателей как идентификаторы.

**Работы.**

- Комментарий преподавателя — одно текстовое поле `teacher_comment`.
- Повторная загрузка — новая независимая запись, версии не связаны.
- Если обработчик упал, работа навсегда остаётся в статусе `PROCESSING`: нет ни статуса сбоя, ни тайм-аута.
- При отзыве работы запись удаляется, а файл в `../storage` остаётся.

**Обмен с обработчиком.**

- Сообщение собирается через `String.format` с подстановкой пути к файлу (`UploadController.uploadFile`); кавычка в имени файла ломает JSON.
- Передаётся абсолютный путь на диске бэкенда — обработчик обязан работать на той же машине.
- В задании нет ни семестра, ни этапа, ни вида работы.

**ИИС.**

- `BsuirApiService.findTeacherByEmail` получает список всех сотрудников и затем делает **отдельный HTTP-запрос на каждого**, пока не найдёт совпадение по почте. Вызывается дважды: при отправке кода и при регистрации. Это сотни и тысячи запросов к ИИС на одну регистрацию.
- Адреса ИИС — константы в коде, подменить их в тестах нельзя.
- Кэши в памяти, сбрасываются раз в час и при перезапуске.
- Обработчик на Python ходит в ИИС независимо, со своим кэшем; `scraper.py` не используется.

**Структура кода.** `UploadController` — 486 строк: регистрация, список работ, отзыв, загрузка и генерация PDF-отчёта в одном классе. Разбор имени файла из пути продублирован в трёх местах. Шрифт для PDF-отчёта ищется по путям `C:/Windows/Fonts/...` — в контейнере Linux кириллицы в отчёте не будет.

## 3. Задачи

Приоритеты: **[A]** — блокирует остальных или прямо из списка задач; **[B]** — нужно к MVP; **[C]** — если останется время.

### К1 [A]. Модель данных и миграции

Перейти на **Flyway**: `V1__baseline.sql` повторяет текущую схему, дальше каждое изменение — отдельная миграция; `ddl-auto=validate` у всех. Альтернатива — Liquibase, но Flyway проще и для нас достаточен.

Целевые изменения:

```
users
  id BIGSERIAL PK                -- внутренний идентификатор, наружу отдаём его
  telegram_id BIGINT UNIQUE
  role, email, url_id
  last_name, first_name, middle_name
  group_number VARCHAR(6)        -- для студентов
  student_card VARCHAR(20) UNIQUE  -- обязателен для студентов, см. К2

iis_groups(number PK, speciality, faculty, course, updated_at)
iis_employees(url_id PK, email, last_name, first_name, middle_name, updated_at)
teacher_groups(teacher_id, group_number)

submissions
  + parent_id                    -- предыдущая версия той же работы
  + original_file_name, storage_key, file_sha256
  + work_type, semester, stage   -- профиль проверки
  + report JSONB                 -- отчёт v2 целиком
  + pipeline_stage               -- текущий этап для индикатора
  статусы: QUEUED, PROCESSING, REJECTED, SUCCESS, FAILED

review_files(id, submission_id, storage_key, original_file_name, uploaded_at)
annotations(id, review_file_id, page, kind, author, created_at,
            comment, quoted_text, rect JSONB, reply_to_id, snapshot_key)
finding_feedback(submission_id, finding_id, teacher_id, verdict, note)
```

Миграция существующих пользователей: разобрать `full_name` тем же регулярным выражением и разложить по новым столбцам; у старых записей будут только инициалы и не будет номера студенческого — при следующем входе попросить дополнить ФИО и указать номер. Поэтому в базе `student_card` допускает `NULL` (старые записи, преподаватели), а обязательность проверяется при регистрации.

Тестового преподавателя убрать из схемы в отдельный `dev-seed.sql`, который не попадает в рабочую базу.

### К2 [A]. Одинаковые имена в одной группе

В базе столкновения нет — пользователи различаются по Telegram ID. Проблема в отображении и в том, что студент сам вводит имя. Сверить введённые данные не с чем: ИИС не отдаёт имена и номера студенческих билетов, поэтому достоверность не проверяется (решение 4 в `docs/decisions.md`). Решение из четырёх слоёв:

1. **Полное ФИО вместо инициалов** — убирает большинство совпадений само по себе.
2. **Номер студенческого билета — обязательное поле для всех студентов**, уникальное в системе. Если номер уже занят, сервер отвечает `409` с кодом `STUDENT_CARD_TAKEN` (название кода согласовать с Халиловым). Что делать, если номер занят по чужой ошибке, — открытый вопрос: настоящему владельцу номера нужен путь к регистрации.
3. **Определение тёзок.** Тёзки — студенты одной группы с полностью совпадающими нормализованными фамилией, именем и отчеством. Нормализация: регистр, «ё» → «е», пробелы, дефисы. Регистрацию совпадение не блокирует.
4. **Единое правило отображения.** В каждом ответе API, где есть студент, сервер отдаёт признак «есть тёзка в группе». Интерфейс помечает таких студентов разными цветами; цвет вычисляется из внутреннего идентификатора студента и не меняется между сеансами. Номер студенческого преподавателю в списках не выводится — он отдаётся отдельным полем и показывается по нажатию на имя (уточняется, см. решение 4). В уведомлениях бота цвета нет — чем различать тёзок там, нужно решить отдельно.

Отдельный случай — тот же человек с второго аккаунта Telegram. Простое решение: считать это совпадением имён и не объединять. Полноценный перенос аккаунта с подтверждением со старого — задача уровня [C].

Дополнительная защита от подмены личности: Бузычков умеет извлекать ФИО с титульного листа. Если оно не совпадает с зарегистрированным, преподавателю показывается предупреждение (не блокировка). Согласовать, в каком поле отчёта это приходит.

Также нужен `PATCH /me` — исправить ФИО, группу или номер студенческого без удаления аккаунта.

### К3 [A]. ИИС: справочники, подсказки, устойчивость

**Единый клиент.** Базовый адрес ИИС — в настройках (`sapsr.iis.base-url`), чтобы Жерко мог подменить его заглушкой в тестах. Тайм-ауты, повтор и «предохранитель» — через Resilience4j (или Spring Retry): после нескольких неудач ИИС считается недоступной на минуту, и запросы не ждут тайм-аута.

**Справочник групп.** Фоновая задача раз в сутки и при старте загружает `/student-groups` в таблицу `iis_groups`. Проверка существования группы и подсказки работают по таблице и не зависят от доступности ИИС в момент регистрации.

Новый метод для подсказок:

```
GET /api/v1/groups?q=3217&limit=10
→ [{ "number": "321701", "speciality": "…", "course": 4 }, …]
```

Поиск по началу номера. Метод вызывается до регистрации — пользователь уже подтверждён подписью Telegram, но ещё не имеет роли; это нормально, только добавить ограничение частоты запросов.

**Справочник преподавателей.** Сначала выяснить, отдаёт ли `/employees/all` почту прямо в списке (в `scraper.py` есть следы полей `email`, `calendarId`, `contactInfo` — проверить живой ответ). Если да — поиск по почте становится одним запросом. Если нет — индекс `iis_employees` строится фоновой задачей раз в сутки, с паузами между запросами, и регистрация ищет по таблице. Перебор всех сотрудников в момент запроса пользователя убрать в любом случае.

**ИИС для обработчика.** Анализатор проверяет код специальности и фамилии на титульном листе, обращаясь в ИИС сам. Договориться с Бузычковым об одном из вариантов: справочники читаются обработчиком из тех же таблиц PostgreSQL; либо бэкенд отдаёт их внутренним методом; либо нужные списки прикладываются к заданию. Первый вариант проще всего.

### К4 [A]. Возврат работы с комментариями преподавателя

Задача из списка: преподаватель комментирует прямо в присланном файле средствами Acrobat, система эти комментарии считывает.

**Сценарий.** Преподаватель скачивает PDF студента → открывает в любом редакторе с аннотациями (Acrobat Reader, Edge, Foxit, Okular, мобильные Adobe и Xodo) → выделяет текст, ставит заметки → сохраняет → загружает обратно → система показывает найденные комментарии → преподаватель выбирает вердикт → студент видит комментарии с привязкой к страницам и может скачать размеченный файл.

**API.**

```
POST /api/v1/teacher/submissions/{id}/review-file     multipart: file
→ { "review_file_id": 12, "annotations": [...], "warnings": [...] }

POST /api/v1/teacher/submissions/{id}/verdict
  { "verdict": "REVISION", "comment": "общий комментарий, необязателен",
    "review_file_id": 12 }

GET  /api/v1/submissions/{id}/annotations             студент и преподаватель
GET  /api/v1/submissions/{id}/review-file             размеченный PDF
```

Общий текстовый комментарий остаётся как необязательное резюме. Правило «на доработку нельзя без комментария» меняется на «нужен либо текст, либо хотя бы одна аннотация».

**Где извлекать аннотации.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Apache PDFBox в бэкенде** | твой стек, синхронно (преподаватель сразу видит результат), лицензия Apache 2.0 | ещё одна PDF-библиотека рядом с OpenPDF |
| PyMuPDF в обработчике | очень удобный API (`page.annots()`, `page.get_textbox(rect)`) | асинхронно через очередь; лицензия AGPL; ещё одна нагрузка на Бузычкова |
| pypdf в обработчике | чистый Python, свободная лицензия | текст под выделением придётся доставать самому |

Рекомендация: PDFBox в бэкенде.

**Что извлекать.** В PDF аннотации — объекты страницы (`PDPage.getAnnotations()`):

| Тип | Что берём |
|---|---|
| Text (заметка-«стикер») | текст заметки, автор, дата, точка на странице |
| Highlight, Underline, StrikeOut, Squiggly | текст комментария **и текст под выделением** — по координатам выделения (`getQuadPoints()`) через `PDFTextStripperByArea`; помнить, что ось Y в PDF направлена вверх |
| FreeText (надпись на странице) | текст, прямоугольник |
| Ink (рисунок от руки), Stamp | текст прочитать нельзя — сохраняем как «пометка на странице N»; по возможности вырезаем картинку области (`PDFRenderer`) |
| ответы на комментарии | связь через «в ответ на» (`getInReplyTo()`), складываем в цепочку |

Всплывающие окна (Popup), ссылки и элементы форм пропускать.

**Проверки при приёме.**

- Файл — действительно PDF, размер в пределах лимита.
- Это тот же документ: совпадает число страниц и текст страниц (аннотации текст не меняют). Не совпало — предупреждение «похоже, загружен другой файл», но не отказ.
- Аннотаций не найдено — предупреждение с подсказкой: скорее всего файл сохранён через «Печать в PDF» и пометки «вплавлены» в страницу. В этом случае файл всё равно прикладывается, а преподавателю предлагается написать текстовый комментарий.

**Комментарии Word не делаем** (решение 3): от студентов принимается только PDF. Если решение изменится, модель `annotations` для этого уже подходит: вместо страницы и прямоугольника — номер абзаца.

**Связь с повторной сдачей [B].** Поле `parent_id` связывает версии. При загрузке новой версии бэкенд прикладывает к заданию аннотации предыдущей; ядро может проверить, изменился ли фрагмент, к которому был комментарий, а интерфейс — показать «учтено / без изменений». Минимум к MVP: связь версий и выдача аннотаций предыдущей версии.

### К5 [A]. Протокол очередей v2

Сообщения — классы-записи, сериализуемые Jackson (`Jackson2JsonMessageConverter`), никакого `String.format`.

```json
// pdf_tasks_queue
{ "schema": 2, "task_id": 153, "type": "CHECK",
  "file": { "storage_key": "2026/10/8f3a….pdf", "sha256": "…" },
  "profile": { "work_type": "course_work", "semester": 7, "stage": 2 },
  "student": { "last_name": "…", "first_name": "…", "group": "321702" },
  "previous": { "task_id": 140, "annotations": [ … ] },
  "trace_id": "…" }

// pdf_progress_queue
{ "task_id": 153, "stage": "structure", "index": 2, "total": 6 }

// pdf_results_queue
{ "schema": 2, "task_id": 153, "phase": "format" | "content" | "failed",
  "report": { … отчёт v2 … }, "trace_id": "…" }
```

Что нужно на стороне бэкенда:

- **Две фазы результата.** `format` приходит быстро: по нему студент получает уведомление об оформлении. `content` приходит позже и дополняет отчёт. Работа уходит преподавателю после `content` либо по тайм-ауту содержательной проверки (решение 5), чтобы сбой модели не блокировал сдачу. Тайм-аут — настройка; пока величина не утверждена, значение по умолчанию 5 минут.
- **Идемпотентность.** Повторно пришедший результат той же фазы не должен слать второе уведомление.
- **Сбой.** Фаза `failed` переводит работу в `FAILED` с понятным сообщением студенту. Плюс сторож по расписанию: работа в `PROCESSING` дольше N минут тоже становится `FAILED`.
- **Очередь недоставленных** (dead-letter): сообщение, которое не удалось разобрать, уходит туда, а не теряется и не крутится по кругу. Настраивается аргументами очереди; согласовать с Жерко.
- **Хранилище файлов.** Вместо абсолютного пути — ключ. Простой вариант: общий том Docker, оба сервиса знают корень из настроек. Вариант с запасом: MinIO (S3-совместимое хранилище). Для курсовой достаточно общего тома; главное — спрятать это за интерфейсом `FileStorage`. Файл сохранять под сгенерированным именем (UUID), исходное имя — только в базе.
- **Прогресс.** Слушатель очереди прогресса пишет `pipeline_stage`; интерфейс получает его обычным опросом `GET /submissions`. Server-Sent Events возможны, но опроса раз в 2–3 секунды достаточно.
- **Trace ID.** Генерируется при загрузке, едет в сообщениях и возвращается в результате — по нему Жерко связывает логи двух сервисов.

### К6 [B]. Шлюз Telegram

Сейчас бот на любое текстовое сообщение отвечает кнопкой и умеет слать текст. Нужно:

- **Работа с файлом прямо в чате.** Когда работа прошла автоматическую проверку, бот отправляет преподавателю сам PDF (`sendDocument`) с подписью и кнопкой «Открыть в кабинете». Преподаватель может **ответить на это сообщение размеченным файлом**: бот сопоставляет `reply_to_message` с уже хранимым `teacher_message_id`, скачивает документ (`getFile`) и передаёт в тот же сервис, что и `POST …/review-file`. Затем спрашивает вердикт кнопками «Принять» / «На доработку» (обработка `callback_query`). Так преподаватель может проверить работу вообще без мини-приложения. Ограничение: через облачный Bot API бот скачивает файлы до 20 МБ, а лимит загрузки в приложении у вас 50 МБ — выровнять.
- **Глубокие ссылки.** Кнопки в уведомлениях открывают мини-приложение сразу на нужной работе (параметр `startapp` в ссылке, в приложении он доступен как `start_param`).
- **Команды** `/start`, `/help`, `/status` (последняя — состояние последних работ).
- **Устойчивость.** Пользователь заблокировал бота — ошибка 403 при отправке; не падать, пометить пользователя и показать предупреждение в интерфейсе. Соблюдать лимиты частоты отправки.
- **Уведомления по отчёту v2**: отдельные счётчики по оформлению и содержанию, пометка «есть замечания, требующие проверки преподавателем».
- **Абстракция.** Выделить интерфейс `Notifier` с реализацией для Telegram: в тестах подставляется заглушка, и сквозные тесты не шлют настоящие сообщения.

Длинный опрос (long polling) оставить: веб-хуку нужен постоянный публичный адрес, а у нас туннель.

### К7 [B]. Порядок в API

- Разрезать `UploadController`: `RegistrationController`, `SubmissionController`, `ReportPdfService`, `SubmissionService`.
- Ответы — классы-записи вместо `Map.of(...)`; единый формат ошибки `{ "code": "DUPLICATE_NAME", "message": "…" }` через `@RestControllerAdvice`. Интерфейсу нужны именно коды, а не тексты.
- **OpenAPI** через springdoc: описание API генерируется из кода, Халилов видит его в Swagger UI, Жерко использует в тестах.
- **Единая проверка доступа.** Сейчас в каждом методе руками повторяется «достать пользователя, сверить роль, сверить владельца». Вынести в `AccessService` или аннотации. Конкретные дыры, которые закрываются по ходу:
  - `POST /upload` не проверяет, что пользователь зарегистрирован как студент, и что `teacher_id` — действительно преподаватель;
  - `GET /submissions/{id}/report`: условие пропускает любого, если у работы не задан студент, и не пускает преподавателя этой работы;
  - `GET /teachers` отдаёт Telegram ID — заменить на внутренние идентификаторы.
- Шрифт для PDF-отчёта положить в ресурсы приложения (PT Serif или DejaVu — свободные лицензии) вместо поиска по системным путям.
- Файлы работ хранятся 6 месяцев с момента загрузки (решение 7), затем удаляются задачей по расписанию. Удалять файл сразу при отзыве работы — в решении 7 это ещё не утверждено, подтвердить; там же открыт вопрос, распространяется ли срок на размеченные преподавателем файлы и отчёты.

### К8 [C]. Версии и сравнение отчётов

`GET /submissions/{id}/diff` — какие замечания исправлены, какие остались, какие появились относительно предыдущей версии. Сопоставление по `requirement_id` и месту. Заявлено в требованиях записки («повторная проверка со сравнением версий»), но к MVP можно ограничиться связью версий.

## 7. Критерии готовности

- схема создаётся миграциями с нуля, `ddl-auto=validate` у всех;
- два студента с одинаковым ФИО в одной группе регистрируются с разными номерами студенческого, в ответах API у обоих стоит признак тёзки; повторный номер студенческого отклоняется;
- регистрация и подсказки групп работают при выключенной ИИС (по справочнику в базе);
- регистрация преподавателя делает не более одного-двух запросов к ИИС;
- файл с заметкой, выделением и ответом на комментарий даёт три правильно связанные аннотации с текстом под выделением;
- при падении обработчика работа получает статус `FAILED`, студент — уведомление;
- ни один метод API не отдаёт Telegram ID других пользователей.
