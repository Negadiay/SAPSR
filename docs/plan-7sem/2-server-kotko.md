## 0. Общий контекст (одинаков во всех четырёх документах)

### Что требует 7-й семестр

Методичка («Требования к системе.pdf») требует **гибридную** систему: символьная часть (база знаний, правила, вывод) и статистическая/нейросетевая часть должны вместе решать одну задачу. Из неё напрямую следует:

- нейросетевой компонент реально участвует в цепочке решения, а не «упомянут»; имитация гибридности прямо названа недопустимой;
- символьный компонент обеспечивает проверяемость и объяснимость итогового решения;
- точки интеграции описаны явно: что, в каком формате и на каком шаге передаётся между компонентами;
- предусмотрена обработка рассогласований: неуверенный ответ модели, отсутствие знаний в базе, противоречие между правилом и моделью;
- компоненты заменяются независимо друг от друга;
- есть методика тестирования: компонентные, интеграционные и сквозные тесты в трёх группах (типичные, граничные, отрицательные), результаты в таблицах;
- есть оценка эффективности (время отклика, нагрузка модели) и, желательно, сравнение гибридного варианта с чисто символьным и чисто нейросетевым.

Во введении и аналитическом разделе записки мы уже пообещали конкретное: распознавание структуры документа нейросетью, извлечение утверждений о системе языковой моделью, поиск противоречий правилами, проверку требований семестра, объяснения с опорой на нормативы.

### Целевая цепочка обработки

```
Mini App (React) ──REST──► Backend (Spring Boot) ──► PostgreSQL
                               │  ▲
              pdf_tasks_queue  │  │  pdf_results_queue, pdf_progress_queue
                               ▼  │
                         Worker (Python)
   1. Извлечение: pdfplumber → символы, строки, координаты
   2. Нейросеть: разметка логических блоков → модель документа
   3. Правила: оформление и структура по каталогу правил из БЗ      ← быстрый результат
   4. LLM: извлечение утверждений, поиск свидетельств (RAG по нормативам)
   5. Правила: конфликты утверждений, вердикт по требованиям семестра, итог
   6. Отчёт v2 → backend → интерфейс
```

## 3. Что сейчас в коде и почему это мешает

Исправленное убрано из списка — оно описано в разделе 4 у своей задачи.

**Данные.**

- Для показа по-прежнему используется строка `full_name`. Регистрация пока принимает старый формат «Иванов И.И. (гр. 321702)», поэтому у новых студентов заполняются только фамилия и группа, а имени нет. Группа для фильтра преподавателей всё ещё достаётся из `full_name` регулярным выражением (`TeacherController.extractGroupNumber`).
- Группы преподавателя — JSON-строка в `users.teacher_groups`.
- `GET /teachers` отдаёт студентам Telegram ID преподавателей как идентификаторы.

**Работы.**

- Комментарий преподавателя — одно текстовое поле `teacher_comment`.

**Обмен с обработчиком.**

- В задании ещё есть переходное поле `file_path` с абсолютным путём — обработчик берёт его, только если нет `storage_key`.

**ИИС.**

- `BsuirApiService.findTeacherByEmail` получает список всех сотрудников и затем делает **отдельный HTTP-запрос на каждого**, пока не найдёт почту. Вызывается дважды: при отправке кода и при регистрации — сотни запросов к ИИС на одну регистрацию.
- Адреса ИИС — константы в коде, подменить их в тестах нельзя.
- Кэши в памяти, сбрасываются раз в час и при перезапуске.
- Обработчик на Python ходит в ИИС сам, со своим кэшем; `scraper.py` не используется.

**Структура кода.** `UploadController` — около 590 строк: регистрация, список работ, отзыв, загрузка и генерация PDF-отчёта в одном классе. Шрифт для PDF-отчёта ищется по путям `C:/Windows/Fonts/...` — в контейнере Linux кириллицы в отчёте не будет.

### К2 [A]. Одинаковые имена в одной группе

Решение 4: полное ФИО; номера студенческого **нет**; в базе тёзки различаются по Telegram ID, а преподаватель видит постоянный номер тёзки — «Иванов Иван Иванович (2)». Что сделать (задачи 4.1–4.3):

1. **Регистрация по полям.** `POST /register` с отдельными фамилией, именем, отчеством и группой, коды ошибок — `api-v1.md`, раздел 4. Плюс `PATCH /me` — исправить ФИО или группу без удаления аккаунта, и `profile_incomplete` в `GET /me` для старых аккаунтов.
2. **Определение тёзок.** Студенты одной группы с совпадающими нормализованными ФИО: регистр, «ё» → «е», пробелы, дефисы. Нормализованное ФИО удобно хранить столбцом `name_key` — по нему и ищутся тёзки. Регистрацию совпадение не блокирует.
3. **Постоянный номер.** `namesake_number` = наибольший номер среди тёзок + 1, первый — 1. Не пересчитывается при удалении аккаунта тёзки; заново выдаётся только при смене ФИО или группы. От одновременных регистраций — уникальный индекс по группе, `name_key` и номеру, при конфликте повтор. Уже зарегистрированным тёзкам номера проставить по дате регистрации.
4. **Отображение.** Везде, где есть студент, — `has_namesake` и `namesake_number` (`api-v1.md`, раздел 2). Telegram ID наружу не отдаётся ни целиком, ни частью. В уведомлениях бота — та же строка с номером.

Отдельный случай — тот же человек со второго аккаунта Telegram: считать совпадением имён и не объединять. Перенос аккаунта с подтверждением со старого — уровень [C].

Защита от подмены личности: Бузычков извлекает ФИО с титульного листа; если оно не совпадает с зарегистрированным — предупреждение преподавателю, не блокировка. Согласовать поле отчёта.

**Что извлекать** (`PDPage.getAnnotations()`):

| Тип | Что берём |
|---|---|
| Text (заметка-«стикер») | текст заметки, автор, дата, точка на странице |
| Highlight, Underline, StrikeOut, Squiggly | текст комментария **и текст под выделением** — по `getQuadPoints()` через `PDFTextStripperByArea`; ось Y в PDF направлена вверх |

| Ink, Stamp | текста нет — «пометка на странице N»; по возможности картинка области (`PDFRenderer`) |
| ответы на комментарии | связь через `getInReplyTo()`, складываем в цепочку |

Всплывающие окна (Popup), ссылки и элементы форм пропускать.

### К6 [B]. Шлюз Telegram

**✅ Сделано 21.10.2026 (за Котко — Халилов):** тексты сообщений — `bot/BotMessages` (HTML, экранирование всего, что пришло от людей); итог проверки студенту и преподавателю, решение преподавателя с перечнем комментариев из файла (номер, страница, начало выделенного текста, комментарий, ответы; до 15 штук, остальное — «в файле»); `/start`, `/help`, ответ на прочий текст; кнопка меню через `SetChatMenuButton` при каждом запуске — настроенная вручную в BotFather кнопка «Войти» вела на устаревший адрес; список команд `SetMyCommands`. Тесты — `BotMessagesTest`, `SapsrTelegramBotTest`.

Было: бот на любое текстовое сообщение отвечал кнопкой и умел слать текст. Нужно:

- **Работа с файлом прямо в чате.** Когда работа прошла автоматическую проверку, бот отправляет преподавателю сам PDF (`sendDocument`) с кнопкой «Открыть в кабинете». Преподаватель может **ответить на это сообщение размеченным файлом**: бот сопоставляет `reply_to_message` с `teacher_message_id`, скачивает документ (`getFile`) и передаёт в тот же сервис, что и `review-file`, затем спрашивает вердикт кнопками (`callback_query`). Через облачный Bot API бот скачивает файлы до 20 МБ, а лимит загрузки в приложении — 50 МБ: выровнять.
- **Глубокие ссылки.** Кнопки в уведомлениях открывают мини-приложение сразу на нужной работе (`startapp` → `start_param`).
- **Команды** `/start`, `/help`, `/status`.
- **Устойчивость.** Пользователь заблокировал бота (403) — не падать, пометить пользователя, показать предупреждение в интерфейсе. Соблюдать лимиты частоты отправки.
- **Уведомления по отчёту v2**: отдельные счётчики по оформлению и содержанию, пометка «есть замечания, требующие проверки преподавателем»; у тёзок — номер в имени.
- **Абстракция.** Интерфейс `Notifier` с реализацией для Telegram; в тестах — заглушка. Тогда и `BackendApplicationTests` можно будет запускать без риска разослать сообщения реальным пользователям.

Long polling оставить: веб-хуку нужен постоянный публичный адрес, а у нас туннель.

## 8. Критерии готовности

- ✅ схема создаётся миграциями с нуля, `ddl-auto=validate` у всех;
- два студента с одинаковым ФИО в одной группе регистрируются без помех, в ответах API у обоих стоит признак тёзки и разные постоянные номера; номер студенческого нигде не запрашивается и не хранится;
- регистрация и подсказки групп работают при выключенной ИИС (по справочнику в базе);
- регистрация преподавателя делает не более одного-двух запросов к ИИС;
- файл с заметкой, выделением и ответом на комментарий даёт три правильно связанные аннотации с текстом под выделением;
- при падении обработчика работа получает статус `FAILED`, студент — уведомление;
- ни один метод API не отдаёт Telegram ID других пользователей.
