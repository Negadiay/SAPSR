## 0. Общий контекст (одинаков во всех четырёх документах)

### Что требует 7-й семестр

Методичка («Требования к системе.pdf») требует **гибридную** систему: символьная часть (база знаний, правила, вывод) и статистическая/нейросетевая часть должны вместе решать одну задачу. Из неё напрямую следует:

- нейросетевой компонент реально участвует в цепочке решения, а не «упомянут»; имитация гибридности прямо названа недопустимой;
- символьный компонент обеспечивает проверяемость и объяснимость итогового решения;
- точки интеграции описаны явно: что, в каком формате и на каком шаге передаётся между компонентами;
- предусмотрена обработка рассогласований: неуверенный ответ модели, отсутствие знаний в базе, противоречие между правилом и моделью;
- компоненты заменяются независимо друг от друга;
- есть методика тестирования: компонентные, интеграционные и сквозные тесты в трёх группах (типичные, граничные, отрицательные), результаты в таблицах;
- есть оценка эффективности (время отклика, нагрузка модели) и, желательно, сравнение гибридного варианта с чисто символьным и чисто нейросетевым.

Во введении и аналитическом разделе записки мы уже пообещали конкретное: распознавание структуры документа нейросетью, извлечение утверждений о системе языковой моделью, поиск противоречий правилами, проверку требований семестра, объяснения с опорой на нормативы.

### Целевая цепочка обработки

```
Mini App (React) ──REST──► Backend (Spring Boot) ──► PostgreSQL
                               │  ▲
              pdf_tasks_queue  │  │  pdf_results_queue, pdf_progress_queue
                               ▼  │
                         Worker (Python)
   1. Извлечение: pdfplumber → символы, строки, координаты
   2. Нейросеть: разметка логических блоков → модель документа

   5. Правила: конфликты утверждений, вердикт по требованиям семестра, итог
   6. Отчёт v2 → backend → интерфейс
```

## 1. Твоя зона и её границы

Слово «оптимизация» в исходном распределении на деле означает четыре направления, и все они сквозные — проходят через все три сервиса:

1. **Тесты** — чтобы не проверять руками;
2. **Наблюдаемость** — логи и перехват ошибок;
3. **Запуск** — воспроизводимый, одной командой;
4. **Безопасность**.

Плюс пятое, которое требуют методичка и записка: **замеры** времени и нагрузки.

Для этого семестра твоя зона — не вспомогательная. В методичке тестированию посвящён отдельный раздел требований, а в критериях недопустимости к 3-й опроцентовке прямо записано «полностью отсутствующее тестирование». Таблицы результатов тестов — обязательная часть записки, и готовишь их ты.

Разграничение: ты строишь инфраструктуру, пишешь сквозные и интеграционные тесты, тесты безопасности и общий каркас. Модульные тесты на свою логику каждый пишет сам в твоём каркасе. Исправления безопасности на уровне инфраструктуры и общих фильтров — твои; исправления бизнес-логики в контроллерах — Котко, по твоему списку.

### Ж1 [A]. Тестовая инфраструктура

Методичка требует тестировать отдельно каждый компонент (база знаний, решатель, модель, интерфейс), их совместную работу и сквозные сценарии. Инструменты по уровням:

| Уровень | Что проверяет | Инструменты |
|---|---|---|
| Модульные, обработчик | каждая проверка оформления; загрузка и проверка каталога правил; правила над фактами; разбор ответа модели | **pytest**, `pytest-cov`; `hypothesis` для числовых границ (допуски полей) |
| Модульные, бэкенд | сервисы, проверка подписи Telegram, извлечение аннотаций | JUnit 5, Mockito, AssertJ |
| Модульные, интерфейс | компоненты, проверка ввода, отображение отчёта | **Vitest** + React Testing Library; **MSW** для подмены API |
| Интеграционные, бэкенд | контроллеры с настоящей базой и очередью | Spring `MockMvc` + **Testcontainers** (PostgreSQL, RabbitMQ); **WireMock** вместо ИИС |
| Интеграционные, обработчик | задание из очереди → отчёт в очередь | pytest + Testcontainers для Python |
| Контрактные | отчёт v2 и сообщения очередей соответствуют схеме с обеих сторон | JSON Schema: один файл схемы, проверка и в pytest, и в JUnit |
| Сквозные | пользователь → интерфейс → бэкенд → обработчик → результат | см. Ж2 |
| Оценка модели | качество нейросетевой части | см. Ж3 |

Что для этого нужно от остальных — попросить на этапе 0:

- у Котко: адрес ИИС и отправка сообщений Telegram — через настройки и интерфейс `Notifier`, чтобы подставлять заглушки;
- у Бузычкова: клиент языковой модели с подменяемой реализацией и режим запуска без модели.

**Подпись Telegram в тестах.** Бэкенд пускает только запросы с корректно подписанными данными запуска. Не добавляй «тестовый обход» проверки — такие обходы попадают в рабочую сборку. Правильно: тестовый профиль с тестовым токеном бота и вспомогательная функция, которая подписывает данные запуска этим токеном по тому же алгоритму HMAC-SHA256 (он реализован в `TelegramInitDataInterceptor`, можно свериться). Функция нужна на Python (для сквозных тестов) и на Java (для `MockMvc`).

**Тестовый корпус.** Основа всех уровней:

- **эталонные документы** — корректно оформленные; генератор уже есть (`generate_valid_sample.py`), добавить эталон в Word и в LaTeX;
- **мутации** — эталон с одним внесённым дефектом на файл: узкое поле, не тот шрифт, пропущен раздел, сбита нумерация рисунков, мало источников. Генерировать скриптом из исходников — тогда ожидаемое замечание известно точно;
- **содержательные дефекты** — три примера из записки (противоречие в форматах входных файлов; онтология против конфигурационного файла; нейросетевой компонент только упомянут) плюс свои;
- **отрицательные** — пустой PDF, скан без текстового слоя, повреждённый файл, не PDF с расширением `.pdf`, зашифрованный PDF, 300 страниц, скрытый белый текст с инструкцией для модели;
- **реальные записки** — наши собственные за прошлые семестры, с ручной разметкой ожидаемых замечаний (размечать вместе с Бузычковым).

Для каждого файла рядом лежит `expected.json`. Чужие работы в репозиторий не класть (см. Ж5, пункт про персональные данные).

**Три группы и таблицы.** Каждый тест помечается группой — типичный, граничный, отрицательный (маркеры pytest, теги JUnit) — и идентификатором вида `E2E-TYP-03`. Методичка требует таблицу: идентификатор, сценарий, задействованные компоненты, ожидаемый результат, фактический, отметка, комментарий. Не заполняй её руками: и pytest, и JUnit, и Playwright умеют писать отчёт в формате JUnit XML; небольшой скрипт собирает из них таблицу в Markdown и LaTeX. Тогда таблица в записке всегда соответствует последнему прогону.

### Ж2 [A]. Сквозные тесты — «чтобы не тыкаться самим»

Два слоя.

**Слой 1: через API, без браузера.** Основной и самый дешёвый.

- Весь стек поднимается в Docker Compose в тестовом профиле: база, очередь, бэкенд, обработчик, WireMock вместо ИИС, заглушка Telegram, языковая модель в режиме воспроизведения записанных ответов.
- Тесты на pytest + `httpx`: подписать данные запуска → зарегистрировать студента и преподавателя → загрузить PDF из корпуса → дождаться результата опросом → сравнить отчёт с `expected.json` → преподаватель загружает размеченный файл и ставит вердикт → проверить, что заглушка Telegram получила нужные уведомления.
- Сценарии — по списку из записки: загрузка и отчёт; повторная сдача; проверка преподавателем с комментариями в файле; полные тёзки в группе (у обоих пометка и разные постоянные номера, номер не меняется после удаления одного из тёзок, решение 4); работа в DOCX (конвертируется в PDF, решение 3); недоступная ИИС; недоступная модель; падение обработчика.

**Слой 2: через интерфейс.** Немного сценариев, самые важные.

- **Playwright.** Мини-приложение — обычная веб-страница, которой нужен объект `window.Telegram.WebApp`. Он подставляется до загрузки страницы (`page.addInitScript`) вместе с подписанными данными запуска.
- Проверять в размере экрана телефона — основной сценарий студента; и в размере окна Telegram Desktop — сценарий преподавателя.
- Сценарии: регистрация с подсказкой группы; загрузка и просмотр отчёта; преподаватель загружает размеченный PDF и видит список комментариев.
- Снимки экрана из Playwright пригодятся для записки и презентации.

**Языковая модель в тестах.** Настоящая модель в сквозных тестах — это минуты и нестабильность. Три режима клиента (делает Бузычков, ты используешь):

- `stub` — заготовленные ответы; для модульных и граничных тестов («модель ответила не по схеме», «модель не уверена», «тайм-аут»);
- `replay` — ответы настоящей модели, один раз записанные в файлы по ключу запроса; для сквозных тестов и CI;
- `live` — настоящая модель; для оценки качества и замеров, запускается вручную или по расписанию.

### Ж3 [B]. Оценка качества гибридной системы

Методичка требует метрики и критерии приемлемости, а записка обещает сравнение вариантов.

- Скрипт оценки прогоняет корпус в трёх режимах ядра (`symbolic`, `neural`, `hybrid` — их обеспечивает Бузычков) и считает: точность и полноту замечаний по категориям; долю ложных срабатываний на эталонах; долю замечаний с цитатой, которой нет в документе; время.
- **Воспроизводимость:** один и тот же файл прогоняется 3–5 раз, отчёты сравниваются. Заявлено как нефункциональное требование.
- **Критерии приемлемости** — предложить команде и записать в записку, например: все сквозные типичные тесты проходят; ни одного аварийного отказа на граничных и отрицательных; оформление документа до 100 страниц — до 60 с; полный отчёт до 60 страниц — до 5 минут; ложные блокирующие замечания на эталонах — ноль. Числа по времени уже заявлены в аналитическом разделе.
- В отчёт о прогоне записывать среду: версии моделей и их квантование, версию каталога правил, железо. Этого тоже требует методичка («зафиксировать процедуру выполнения тестов»).

### Ж4 [A]. Логирование и перехват ошибок

**Бэкенд.**

- SLF4J и Logback вместо `System.out` и `printStackTrace`; уровни — через настройки; `show-sql` выключить.
- Формат — JSON-строки (`logstash-logback-encoder` либо встроенное структурированное логирование Spring Boot): такие логи потом фильтруются по полям.
- **Сквозной идентификатор.** Фильтр на входе создаёт `trace_id`, кладёт его в MDC (попадает в каждую строку лога), в сообщение очереди и в ответ клиенту. По нему одна загрузка прослеживается через оба сервиса.
- Общий обработчик исключений (`@RestControllerAdvice`): клиент получает код ошибки и `trace_id`, подробности — только в лог. Сейчас, например, клиенту уходит текст исключения почтового сервера.
- Spring Boot Actuator: `/actuator/health` для проверок готовности в Docker; метрики через Micrometer.

**Обработчик.**

- Модуль `logging` или `structlog` с выводом JSON; `trace_id` и `task_id` — в каждой записи.
- Обработка задания — в `try/except`: на любую ошибку отправляется результат со статусом сбоя, сообщение подтверждается. Неразбираемые сообщения — в очередь недоставленных (настраивается вместе с Котко).
- Время каждого этапа цепочки — в лог и в раздел `pipeline` отчёта. Это же источник цифр для Ж6.
- Тайм-аут на проверку в целом: зависшая модель не должна держать очередь.

**Интерфейс.**

- Граница ошибок React (`ErrorBoundary`) с понятным экраном вместо белой страницы.
- Обработчики `window.onerror` и `unhandledrejection` отправляют ошибку на `POST /api/v1/client-log` (метод сделает Котко). С ограничением частоты и без содержимого полей ввода.

**Сбор и просмотр.**

| Вариант | Когда выбирать |
|---|---|
| `docker compose logs` + `jq` | минимум, работает сразу |
| Grafana + Loki | все логи в одном окне с поиском по `trace_id`; около трёх контейнеров |
| GlitchTip (совместим с Sentry) | группировка ошибок и трассировки стека из всех трёх сервисов; есть готовые клиенты для Spring, Python и браузера |
| OpenTelemetry + Jaeger | полноценная трассировка; для нас избыточно |

Рекомендация: JSON-логи с `trace_id` обязательно; Loki с Grafana — если останется время, это хорошо смотрится на защите.

**Чего в логах быть не должно:** данные запуска Telegram, токен бота, коды подтверждения, текст работ, полные ФИО с Telegram ID в одной строке.

## 7. Критерии готовности

- на чистой машине с Docker система поднимается одной командой по README;
- сквозные тесты запускаются одной командой и не требуют Telegram, ИИС и видеокарты;
- есть тесты всех трёх групп на каждом уровне; таблица для записки собирается скриптом;
- по `trace_id` находится полный путь одной загрузки в логах обоих сервисов;
- падение обработчика на любом документе корпуса не останавливает очередь;
- все пункты высокого приоритета из Ж5 закрыты, на каждый есть тест;
- в репозитории и его истории нет действующих секретов и чужих персональных данных.
