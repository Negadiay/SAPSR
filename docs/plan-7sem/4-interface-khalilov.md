## 0. Общий контекст (одинаков во всех четырёх документах)

### Что требует 7-й семестр

Методичка («Требования к системе.pdf») требует **гибридную** систему: символьная часть (база знаний, правила, вывод) и статистическая/нейросетевая часть должны вместе решать одну задачу. Из неё напрямую следует:

- нейросетевой компонент реально участвует в цепочке решения, а не «упомянут»; имитация гибридности прямо названа недопустимой;
- символьный компонент обеспечивает проверяемость и объяснимость итогового решения;
- точки интеграции описаны явно: что, в каком формате и на каком шаге передаётся между компонентами;
- предусмотрена обработка рассогласований: неуверенный ответ модели, отсутствие знаний в базе, противоречие между правилом и моделью;
- компоненты заменяются независимо друг от друга;
- есть методика тестирования: компонентные, интеграционные и сквозные тесты в трёх группах (типичные, граничные, отрицательные), результаты в таблицах;
- есть оценка эффективности (время отклика, нагрузка модели) и, желательно, сравнение гибридного варианта с чисто символьным и чисто нейросетевым.

Во введении и аналитическом разделе записки мы уже пообещали конкретное: распознавание структуры документа нейросетью, извлечение утверждений о системе языковой моделью, поиск противоречий правилами, проверку требований семестра, объяснения с опорой на нормативы.

### Целевая цепочка обработки

```
Mini App (React) ──REST──► Backend (Spring Boot) ──► PostgreSQL
                               │  ▲
              pdf_tasks_queue  │  │  pdf_results_queue, pdf_progress_queue
                               ▼  │
                         Worker (Python)
   1. Извлечение: pdfplumber → символы, строки, координаты
   2. Нейросеть: разметка логических блоков → модель документа
   3. Правила: оформление и структура по каталогу правил из БЗ      ← быстрый результат
   4. LLM: извлечение утверждений, поиск свидетельств (RAG по нормативам)
   5. Правила: конфликты утверждений, вердикт по требованиям семестра, итог
   6. Отчёт v2 → backend → интерфейс
```

### 8. Задачи

Приоритеты: **[A]** — прямо из списка задач или блокирует показ; **[B]** — нужно к MVP; **[C]** — если останется время.

#### И1 [A]. Разбор монолита

Сделать до новых экранов, иначе каждая следующая задача будет дороже.

```
src/
  api/          client.js (заголовок авторизации, разбор ошибок по кодам), методы по разделам
  features/
    registration/   формы студента и преподавателя, подсказка группы
    student/        загрузка, список работ, отчёт
    teacher/        очередь, проверка работы, история, заметки
    report/         отображение отчёта v2 — общее для обеих ролей
    settings/       тема, размер шрифта, контраст, обучение
  components/   кнопки, поля, списки с подсказками, уведомления
  telegram/     обёртка над window.Telegram.WebApp
```

- **Серверное состояние** — TanStack Query: кэш, повторные попытки, а главное — опрос статуса работы по интервалу без ручных таймеров. Альтернатива — SWR.
- **Навигация** — текущих вкладок достаточно; маршрутизатор нужен только для открытия конкретной работы по ссылке из уведомления (`start_param`), и это решается одним условием при старте.
- **TypeScript** — по желанию. Если переходить, то начиная с `api/` и типов отчёта: именно там ошибки дороже всего. Типы можно сгенерировать из OpenAPI (`openapi-typescript`).
- **Стили** — разнести по компонентам (CSS Modules поддерживаются Vite без настройки). Переменные тем оставить общими.
- Расставить `data-testid` на ключевых элементах — их использует Жерко в сквозных тестах.

#### И2 [A]. Регистрация с подсказками

Одно поле заменить формой:

- **Фамилия, имя, отчество** — три поля; переключатель «нет отчества». Заглавная буква ставится автоматически; пробелы по краям обрезаются. Имя и фамилию из профиля Telegram можно предложить как подсказку под полем («Подставить: …»), но не заполнять молча — там часто не настоящие имена.
- **Группа** — поле с выпадающим списком:
  - цифровая клавиатура (`inputmode="numeric"`), не больше шести цифр;
  - после двух введённых цифр — запрос `GET /api/v1/groups?q=…` с задержкой 200–300 мс после последнего нажатия;
  - в списке до восьми вариантов: номер, специальность, курс — например «321702 · Искусственный интеллект · 4 курс»;
  - выбор касанием и с клавиатуры (стрелки, Enter, Esc); разметка по шаблону ARIA «combobox», чтобы работали программы чтения с экрана;
  - введено шесть цифр, совпадений нет — сразу «Такой группы нет в ИИС», не дожидаясь отправки формы;
  - справочник недоступен — поле работает как обычное, проверку делает сервер.

  Библиотеки, если не писать самому: Downshift, Headless UI (Combobox), React Aria. Список короткий, логика простая — можно и самому, но доступность в готовых уже сделана.

  Вариант проще: один раз загрузить весь список групп и фильтровать на клиенте. Отклик мгновенный, но запрос тяжелее. Размер справочника замерен 18.10.2026: в ИИС 426 групп, ответ ИИС — около 190 КБ, а список только из номера, сокращения специальности и курса — около 29 КБ без сжатия. Это вполне можно грузить целиком.
- **Номер студенческого билета не запрашивается** (решение 4 в редакции 18.10.2026): тёзки различаются по Telegram ID, вводить для этого ничего не нужно.
- **Проверка по ходу ввода**: ошибка появляется под полем, когда пользователь из него вышел, и пропадает при исправлении. Кнопка отправки неактивна, пока форма неполная.
- **Преподаватель**: при вводе адреса без домена — подсказка-кнопка «@bsuir.by»; поле кода — `inputmode="numeric"` и `autocomplete="one-time-code"`; после успешной проверки почты показать найденное в ИИС ФИО для подтверждения.
- **Ошибки сервера — по кодам** из `docs/contracts/api-v1.md` (`GROUP_NOT_FOUND`, `VALIDATION_ERROR` с именем поля и другие), а не по тексту. Совпадение ФИО регистрацию не блокирует и при регистрации не сообщается; студент с тёзкой видит только свой номер в «Мои данные».
- В настройках — экран «Мои данные» с возможностью исправить ФИО и группу. Если в группе есть тёзка, там же — свой номер («Среди студентов группы с таким же ФИО вы — №2») с пояснением: назовите его преподавателю, если он спросит, кто из вас кто. Если тёзки нет, номер не показывается.
- Пользователям, зарегистрированным по старой форме (только инициалы), при входе предложить дополнить ФИО: сервер отдаёт признак `profile_incomplete`.

#### И3 [A]. Проверка работы преподавателем: комментарии в файле

Сценарий: скачать работу → прокомментировать в привычной программе → загрузить обратно → увидеть, что система прочитала → вынести вердикт.

Экран проверки одной работы:

1. **Скачать PDF.** В мини-приложении скачивание из встроенного браузера работает ненадёжно. В свежих версиях клиентов есть метод `Telegram.WebApp.downloadFile` — ему нужен адрес, доступный без заголовков, то есть одноразовая короткоживущая ссылка от бэкенда (она же заменит небезопасный параметр `tg_auth`, см. план Жерко). Запасной путь — кнопка «Прислать файл в чат»: бот отправляет PDF сообщением.
2. **Короткая инструкция**, раскрывающаяся по нажатию: «Откройте файл в Acrobat Reader, Edge или другой программе с комментариями. Выделяйте текст, добавляйте заметки. Сохраните файл обычным сохранением, не через печать».
3. **Загрузка размеченного файла**: область перетаскивания на компьютере, кнопка выбора на телефоне; индикатор загрузки.
4. **Предпросмотр извлечённого** — список по страницам: тип пометки, выделенный текст цитатой, комментарий. Преподаватель видит, что всё прочиталось, до отправки студенту. Предупреждения сервера показывать заметно: «комментариев не найдено — возможно, файл сохранён через печать», «похоже, это другой документ».
5. **Вердикт**: «Принять» / «На доработку» и необязательный общий комментарий. Шаблоны комментариев сохранить.

Сторона студента:

- в карточке работы — раздел «Комментарии преподавателя»: список по страницам с цитатами, цепочки ответов сворачиваются;
- кнопка «Скачать файл с комментариями»;
- рукописные пометки и штампы показываются как «пометка на странице N» (с картинкой области, если сервер её отдаёт).

**Просмотр прямо в приложении [B].** `pdfjs-dist` или обёртка `react-pdf`: показать размеченный PDF с включённым слоем аннотаций — пометки рисует сама библиотека; нажатие на комментарий в списке прокручивает к странице. Для телефона это важнее, чем для компьютера.

**Комментирование прямо в приложении [C].** У PDF.js есть встроенный редактор пометок (выделение, текст, рисование). Это позволило бы обойтись без сторонней программы, но объём работы большой, а на телефоне выделять текст в PDF неудобно. Только после MVP.

Заметки преподавателя и шаблоны: перенести из `localStorage` в `Telegram.WebApp.CloudStorage` — хранится в облаке Telegram на пользователя, работает на всех устройствах, сервер не нужен. Проверить лимиты на размер значения перед переносом.

#### И4 [A]. Отчёт v2

Общий компонент для студента и преподавателя.

- **Сводка**: итог, счётчики по категориям — оформление, структура, содержание; отдельно — «требуют проверки преподавателем».
- **Группировка и фильтры**: по категории, серьёзности, странице.
- **Карточка замечания**: сообщение; что ожидалось и что найдено; цитаты из документа с номером страницы и раздела; источник требования («СТП 01-2024, п. …»); рекомендация.
- **Противоречие** — два фрагмента рядом (на телефоне — один под другим) с подписями разделов и подсветкой расходящихся значений. Ради этого и нужен новый формат.
- **Происхождение**: метка «правило», «модель» или «правило + модель» с пояснением по нажатию. Это честно по отношению к студенту и наглядно показывает гибридность на защите.
- **Уверенность**: не процент, а три уровня словами; низкая уверенность — пометка «требует проверки преподавателем», визуально отличающаяся от ошибок.
- **Пропущенные проверки**: блок «Не проверено» с причинами из раздела `pipeline` («справочник ИИС недоступен», «языковая модель недоступна»).
- **«Объяснить»** в карточке: запрос объяснения с опорой на норматив по требованию; состояние загрузки; текст с указанием пункта.
- **Сведения о проверке** в свёрнутом виде: версии моделей и базы правил, время по этапам — требование воспроизводимости из записки.

Пока бэкенд и интерфейс переходят на новый формат, компонент должен уметь показать и старый отчёт.

#### И5 [B]. Загрузка работы и ход проверки

- При загрузке — выбор **вида работы, семестра и этапа опроцентовки** (от них зависит профиль требований). Предзаполнять последним выбором; курс можно предложить по номеру группы.
- **Индикатор этапов** вместо общей анимации: «Извлечение текста → Структура → Оформление → Содержание → Отчёт». Заявлено в требованиях («с отображением этапов обработки»). Данные — поле этапа в ответе списка работ, опрос раз в 2–3 секунды.
- **Двухфазный результат**: результат по оформлению показывается сразу, содержательная часть — «ещё проверяется».
- Состояние сбоя (`FAILED`) с понятным текстом и кнопкой «Загрузить снова».
- Проверка на клиенте до отправки: тип (PDF или DOCX, решение 3) и размер файла.
- Если работа пришла в DOCX — пометка «проверена PDF-версия» и кнопка её скачать: номера страниц в отчёте относятся к ней.

#### И6 [B]. Кабинет преподавателя

- **Обратная связь по замечаниям**: «верно» / «неверно» у каждого замечания, особенно у тех, что требуют проверки. Это и требование из записки, и данные для подбора порогов у Бузычкова.
- **Карта покрытия требований семестра**: таблица «требование → статус → свидетельство», по нажатию — цитата.
- **Тёзки** (решение 4 в редакции 18.10.2026): сервер отдаёт у студента признак `has_namesake` и постоянный номер `namesake_number`. Цветом не помечаем: рядом с именем — номер в скобках и значок «тёзка», «Иванов Иван Иванович (2)». Номера могут идти с пропусками — показывать как есть, не перенумеровывать. У значка — текстовая подпись для программ чтения с экрана; проверить в режиме высокой контрастности.
- Очередь: фильтр по группе, признак «повторная сдача» со ссылкой на предыдущую версию и её комментарии.

#### И7 [C]. Сравнение версий

При повторной сдаче — три списка: исправлено, осталось, появилось. Плюс отметки у комментариев преподавателя к прошлой версии: «фрагмент изменён» / «без изменений». Зависит от задач уровня [C] у Котко и Бузычкова.

#### И8 [B]. Тесты и устойчивость интерфейса

- **MSW** — подмена ответов API: разработка без бэкенда и основа тестов.
- **Vitest + React Testing Library**: проверка полей регистрации; список подсказок групп (задержка, пустой результат, ошибка сервера, управление с клавиатуры); отчёт v2 на примерах из контракта, включая пограничные — пустой отчёт, сто замечаний, очень длинная цитата, замечание без места в документе.
- **Граница ошибок** и отправка ошибок на сервер — совместно с Жерко.
- Единый показ ошибок сервера по кодам, а не по тексту; состояния «нет сети» и «сервер недоступен».
- Проверить в Telegram на iOS, Android и на компьютере: клавиатура, перекрывающая поля; безопасные отступы; кнопка «Назад»; тёмная тема; уже реализованные размер шрифта и контраст — на новых экранах.

### 11. Критерии готовности

- регистрация студента проходит без единого сообщения «неверный формат» после отправки — все ошибки видны при вводе;
- группа выбирается из списка после двух-трёх цифр; при недоступном справочнике форма остаётся рабочей;
- полные тёзки в одной группе различимы в списке преподавателя, в том числе в режиме высокой контрастности;
- противоречие показывается двумя фрагментами с разделами и страницами;
- у каждого замечания видно происхождение; замечания «на проверку преподавателю» визуально отличаются от ошибок;
- преподаватель проходит путь «скачать → загрузить размеченный файл → увидеть комментарии → вердикт» на компьютере и на телефоне;
- студент видит комментарии преподавателя по страницам и может скачать размеченный файл;
- `App.jsx` разобран, каждый новый экран покрыт тестами на примерах из контрактов.
