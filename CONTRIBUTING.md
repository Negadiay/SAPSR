# Работа с Git в проекте

Короткие правила, чтобы изменения четырёх человек не мешали друг другу. Команды одинаково работают в PowerShell, cmd и bash.

Везде ниже `<моя-ветка>` — твоя личная ветка из таблицы.

## Ветки

| Ветка | Зачем | Кто туда пишет |
|---|---|---|
| `main` | стабильная версия, которую показываем | никто напрямую; только слияние из `dev` через запрос на слияние |
| `dev` | общая тестовая ветка, здесь сходятся изменения всех | никто напрямую; только слияние из личных веток через запрос на слияние |
| личная | твоя текущая работа | только ты |

| Участник | Личная ветка |
|---|---|
| Бузычков | `negadiay` |
| Жерко | `urozy` |
| Котко | `kamanoku` |
| Халилов | `ithinkbee` |

Изменения движутся в одну сторону: личная ветка → `dev` → `main`.

## Один раз в начале

```bash
git fetch origin --prune
git checkout <моя-ветка>
```

`--prune` убирает у тебя ссылки на ветки, которые уже удалены на GitHub.

## Каждый раз перед работой

```bash
git checkout <моя-ветка>
git pull origin <моя-ветка>     # свои изменения с другого компьютера, если были
git pull origin dev             # чужие изменения из общей ветки
```

Вторую команду не пропускать. Чем дольше ветка живёт без обновления из `dev`, тем больше конфликтов потом.

## Во время работы

```bash
git status                      # посмотреть, что изменилось
git add <файл> <файл>           # добавить нужные файлы
git commit -m "Что сделано"
git push origin <моя-ветка>
```

- Перед `git add` смотри `git status`. Команда `git add .` добавляет всё подряд — используй её, только если в списке нет лишнего.
- Коммить часто и небольшими частями: одна задача — один или несколько коммитов.
- В сообщении коммита пиши, что изменилось: «Регистрация: подсказка группы», а не «update» или «fix».
- Отправляй (`push`) в конце каждого рабочего дня, даже если не закончил: так работа не пропадёт и видна остальным.

## Как добавить свои изменения в `dev`

Делается через запрос на слияние (Pull Request) на GitHub, когда часть работы готова и не ломает запуск.

**1. Подтяни `dev` в свою ветку и проверь, что всё работает.**

```bash
git checkout <моя-ветка>
git pull origin dev
```

Если появились конфликты — разреши их у себя (раздел «Конфликты» ниже). После этого запусти систему и убедись, что она поднимается.

**2. Отправь ветку.**

```bash
git push origin <моя-ветка>
```

**3. Открой запрос на слияние на GitHub.**

- Вкладка **Pull requests** → **New pull request**.
- **base:** `dev`, **compare:** `<моя-ветка>`. Проверь это дважды: по умолчанию GitHub подставляет `main`.
- В описании — что сделано и как проверить.
- Назначь проверяющим любого другого участника.

**4. Дождись проверки и слей.**

- Сливать кнопкой **Create a merge commit**. Варианты **Squash and merge** и **Rebase and merge** не использовать: личные ветки живут долго, и после них каждое следующее слияние будет давать конфликты на уже слитом коде.
- Личную ветку после слияния **не удалять** — кнопку «Delete branch» не нажимать.

**5. Обнови свою ветку.**

```bash
git pull origin dev
```

Остальным после чужого слияния в `dev` достаточно обычного `git pull origin dev` перед работой.

## Из `dev` в `main`

Делает руководитель группы, когда `dev` проверена целиком: запрос на слияние `dev` → `main`. Остальным в `main` ничего отправлять не нужно.

## Конфликты

Конфликт возникает, когда ты и кто-то ещё изменили одни и те же строки. Git останавливается и пишет `CONFLICT` с именами файлов.

1. Открой каждый такой файл. Конфликтное место выглядит так:

   ```
   <<<<<<< HEAD
   твой вариант
   =======
   вариант из dev
   >>>>>>> ...
   ```

2. Оставь правильный вариант (свой, чужой или объединённый) и удали все три строки-маркера.
3. Заверши слияние:

   ```bash
   git add <файл>
   git commit
   ```

Если непонятно, чей вариант верный, — спроси автора второго изменения, не выбирай наугад. Отменить начатое слияние и вернуться к состоянию до него:

```bash
git merge --abort
```

## Чего не делать

- **Не отправлять напрямую в `main` и `dev`** — только через запрос на слияние.
- **Не использовать `git push --force`** ни на одной ветке. Если Git не даёт отправить — сначала `git pull`.
- **Не делать `git rebase`** на уже отправленных ветках.
- **Не коммитить секреты и локальные настройки:** `.env`, `application.properties`, токен бота, пароли. Они в `.gitignore`; если Git всё равно показывает такой файл в `git status` — не добавляй его и напиши в чат.
- **Не коммитить чужие работы и персональные данные** (реальные PDF студентов, Telegram ID).
- **Не работать в чужой личной ветке.** Нужно чужое изменение — попроси автора слить его в `dev`.

## Если что-то пошло не так

**Начал править не в той ветке, ещё не закоммитил.**

```bash
git stash
git checkout <моя-ветка>
git stash pop
```

**Закоммитил не в ту ветку, ещё не отправил.**

```bash
git log --oneline -3            # скопируй хэш своего коммита
git checkout <моя-ветка>
git cherry-pick <хэш>
```

После этого напиши в чат: лишний коммит из той ветки нужно убрать аккуратно, вместе разберёмся.

**Отменить последний коммит, сохранив изменения в файлах** (только если ещё не отправил):

```bash
git reset --soft HEAD~1
```

**Отменить уже отправленный коммит** — новым коммитом, который делает обратное:

```bash
git revert <хэш>
git push origin <моя-ветка>
```

**Вернуть один файл к последнему закоммиченному состоянию** (несохранённые правки в нём пропадут):

```bash
git restore <файл>
```

**Не уверен, что делаешь, — остановись и спроси.** Почти всё в Git можно восстановить, пока не сделан `push --force` и не удалена папка проекта.
