# Проектирование проверки: правило или модель

Главная идея гибридного ядра SAPSR: **модель только достаёт факты из текста, решение выносит правило.** Всё, что можно проверить детерминированно, проверяется без модели — это дешевле, воспроизводимо и объяснимо преподавателю. Модель подключается только там, где без понимания смысла не обойтись, и каждый её ответ проходит символьную проверку.

## Как выбрать

```
Можно ли проверить по геометрии, шрифтам, тексту по шаблону?
├── Да → проверка оформления: sapsr/checks/ + правило в kb/rules/*.yaml. Модель не нужна.
└── Нет, нужен смысл текста
    ├── Есть закрытый список значений (форматы, технологии, роли)?
    │   └── Модель извлекает утверждения по JSON-схеме → verify (цитата есть в тексте)
    │       → normalize (значение из kb/concepts.yaml) → правило CLIPS в kb/reasoning/claims.clp
    ├── Это требование семестра («есть диаграмма вариантов использования»)?
    │   └── kb/requirements/<семестр>.yaml → BM25 отбирает кандидатов → модель: supports |
    │       contradicts | irrelevant + цитата → verify → kb/reasoning/requirements.clp
    └── Ничего из этого → сначала подумать ещё раз. Свободный вывод модели (sapsr/content/neural.py)
        у нас только как вариант для сравнения в метриках, замечания из него не блокируют сдачу.
```

Признаки того, что модель не нужна: проверка формулируется числом (поля, кегль, отступ), шаблоном (номер рисунка, «Таблица N – …», запись в списке источников по ГОСТ) или наличием/порядком раздела. Такие вещи через модель делать нельзя — будут случайные ошибки там, где их быть не может.

## Обязательные свойства любой проверки с моделью

1. **Схема ответа.** Модель отвечает строго по JSON-схеме; допустимые атрибуты берутся из словаря понятий, свои модель не придумывает. Подсказка — файл `kb/prompts/<имя>.vN.md`; меняешь смысл подсказки — поднимаешь версию (ключ кэша ответов включает версию).
2. **Цитата обязательна и проверяется** (`sapsr/content/verify.py`, нечёткое сравнение rapidfuzz). Нет цитаты в тексте — ответ отбрасывается и идёт в метрику «доля выдуманных цитат».
3. **Уверенность.** Итоговая уверенность замечания — наименьшая из уверенностей его фактов; ниже `review_threshold` профиля (`kb/profiles/base.yaml`, сейчас 0,75) — «требует проверки преподавателем». Содержательные замечания не блокируют сдачу (решение 5).
4. **Модель может отсутствовать.** Режим `off` или недоступная модель → этап в `pipeline.skipped`, а не «замечаний нет».
5. **Персональные данные.** Для облачной модели текст проходит `sapsr/llm/privacy.py`; титульный лист в модель не идёт. Новая проверка не должна отправлять в модель то, что обходит эту защиту.
6. **Текст для модели — только нужные фрагменты** (`sapsr/content/fragments.py`), с идентификаторами блоков, чтобы правило нашло страницу и раздел.

## Как добавить проверку оформления

1. Функция проверки в нужном модуле `sapsr/checks/` и регистрация в реестре (`sapsr/checks/registry.py`) со своей pydantic-схемой параметров.
2. Числа (допуски, нормы) — только в параметрах правила, не в коде.
3. Правило в `kb/rules/NN-*.yaml`: `id`, `title`, `category`, `source` (пункт норматива проставлять только по тексту СТП, иначе `clause: null`), `severity`, `blocking`, `check`, тексты `message`/`expected`/`found`/`fix` — их видит студент, писать понятно и по-русски.
4. Тест в `tests/test_checks.py`; документы для теста — через `tests/rawdoc.py`.

## Как добавить содержательную проверку

1. Понятия и синонимы — `kb/concepts.yaml`; правило вывода — `kb/reasoning/*.clp`; описание замечания (тексты, серьёзность, источник) — `kb/rules/50-content.yaml`.
2. Если нужен новый вид ответа модели — новая подсказка `kb/prompts/<id>.vN.md` и схема; действующая версия подсказки указывается в `kb/catalog.yaml` (раздел `prompts`). Старую версию подсказки не переписывать.
3. Тесты без настоящей модели: `tests/scripted_llm.py` (`ScriptedModel`, в том числе с `hallucinate=True` — проверка, что выдуманные цитаты отбрасываются) и режим `stub` клиента. Сквозные тесты — режим `replay` с ответами из `test-fixtures/llm-replay`; новые ответы записываются режимом `record` на локальной модели.
4. Ожидаемые результаты по `test-fixtures/hybrid/*.pdf` — `tests/test_fixtures_expected.py`.

## Проверка

Из `worker-python`, интерпретатор из venv:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check sapsr
```

Ruff: в коде есть старые замечания — сравнивать число с `HEAD`, а не требовать ноль. Живой прогон на Ollama (`qwen3.5:4b`) — по желанию, только на тестовых записках, не на работах настоящих студентов.

## Для записки и диплома

Аргументы в пользу гибридной схемы, которые стоит приводить: воспроизводимость (детерминированные проверки, `temperature=0`, кэш ответов), объяснимость (каждое замечание — правило с источником и цитатой), защита от галлюцинаций (проверка цитат и метрика выдуманных цитат), заменяемость компонентов (модель — параметр, решатель CLIPS — отдельный модуль), сравнение с чисто нейросетевым вариантом (`neural.py`) по метрикам.
